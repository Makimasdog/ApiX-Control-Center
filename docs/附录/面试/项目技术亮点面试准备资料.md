## 3. 两个项目如何区别，避免混讲

| 维度 | MewCode | ApiX |
| --- | --- | --- |
| 主要定位 | 编程 Agent、子 Agent 与运行服务 | 管理多个独立 CLI 员工的协调平台 |
| 技术主线 | Python、asyncio、工具调用、MCP、FastAPI | Node.js、TypeScript、SQLite、进程托管、Git |
| 任务编排 | `DAGScheduler` 按批次运行就绪节点 | 根据数据库依赖状态及验收门槛推进任务 |
| 持久化 | JSON 快照、JSONL 事件日志 | SQLite 状态表、运行事件、协调账本与快照 |
| 恢复方式 | `recover()` 重新调度未完成 Run | 未完成运行标记 unknown，经检查后新建运行 |
| MCP | 有 Client、Manager、ToolWrapper 代码 | CLI Adapter 和 Mailbox 本身不是 MCP |
| 工作区 | 子 Agent/团队路径可使用 worktree | 托管 worktree、冻结交付与依赖代码交接 |

两者的递进可以这样讲：

> MewCode 关注 Agent 怎样通过工具完成工作；ApiX 更关注多个 Agent 怎样在权限、依赖和验收约束下协作交付。

## 4. ApiX 项目介绍：约两分钟

> ApiX 是一个面向本机项目的多 Agent 协作平台。用户先提出目标，管理者通过 Pi 整理需求和执行计划，再分派给 Codex、Claude 等独立 CLI 员工。
>
> 这里的难点是协作过程的一致性。第一，需求和权限会变化，所以执行前需要检查版本，防止旧批准继续生效；第二，任务有依赖，员工退出成功不代表成果已验收，下游要等前置交付通过；第三，不同 CLI 的事件格式不同，需要统一采集结果、错误和已报告用量；第四，并行改代码需要独立工作区和可靠交接，不能只把员工回复当作代码已经集成。
>
> 当前系统用 SQLite 保存状态和事件轨迹，用独立 Git worktree 执行任务，验收后冻结交付给下游。我的实际参与是【真实职责】，其中最熟悉的部分是【选择一个亮点】，可以展开说明实现和验证。

### 一条必须能画出来的调用链

```text
前端请求
  → server.mjs：解析路由、请求和 SSE
  → coordinator.ts：沟通、确认需求、生成/派发计划
  → 权限与计划版本校验、预算和并发准入
  → resolveApproval / 调度器
  → launch：创建运行、工作区、员工凭据和 CLI 子进程
  → 解析原生事件，回写状态、结果和用量
  → 差异审查与验收，冻结代码交付
  → 调度依赖任务
```

区分五个对象：Project 是项目；Session 是一次目标会话；Plan 是执行方案；Task 是工作项；Run 是一次实际运行。一个 Task 重试时可以有多个 Run。

## 5. ApiX 亮点一：事件账本与历史状态查询

### 5.1 面试先说这段

> 多 Agent 执行中，仅保存最新状态很难解释为什么这样派发、谁批准过、权限何时变化。ApiX 在业务状态之外追加协调事件，并保存关键阶段的会话快照，可以按事件序号查看历史状态和决策轨迹。当前实现是事件账本加快照，不是整个系统只靠事件重建的严格事件溯源架构。

### 5.2 实现细节

证据：[memory.ts](../../../src/memory.ts)、[coordinator.ts](../../../src/coordinator.ts)。

1. `apix_ledger` 保存自增 `sequence`、项目 ID、聚合 ID、类型、行为者、JSON payload、时间及 schema 版本字段。这里的 schema 字段不代表已实现完整事件迁移框架。
2. `append()` 负责插入事件。项目、聚合及组合索引服务于按对象查历史。
3. `checkpoint(sessionId)` 读取会话、解析后的需求和当前任务，追加 `coordination.snapshot`。
4. 部分协调操作使用 `BEGIN/COMMIT/ROLLBACK` 把业务更新和事件写入放在同一事务里。不能推导成所有模块所有事件都具有这一保证。
5. `events()` 取指定序号以前最近 200 条，再按升序返回；`previousAt` 用于继续查更早记录。
6. `stateAt()` 单独查询指定序号前最近快照，因此即使快照不在当前 200 条事件中，仍能读到它。
7. `search()` 在 SQLite 中通过自定义函数做不区分大小写的字面包含匹配，最多返回最近 50 个匹配，不是向量检索。

**核心查询，按源码整理：**

```sql
SELECT payload
FROM apix_ledger
WHERE project_id = ? AND aggregate_id = ?
  AND sequence <= ? AND kind = 'coordination.snapshot'
ORDER BY sequence DESC
LIMIT 1;
```

### 5.3 典型追问

**为什么用序号，不只用时间？**

序号提供明确的查询顺序和翻页边界，时间戳可能相同。这里是同一数据库的全局顺序，不能推广为分布式全局时钟。

**Append-only 是不是防篡改？**

当前写入路径按追加使用，没有密码学防篡改链或只写存储保证。能追踪历史不等于管理员无法修改数据库。

**能恢复任意时刻完整状态吗？**

能查看该序号前最近的协调快照和事件；没有通用 reducer 把所有后续事件逐个重算到精确进程状态，也不恢复文件和外部副作用。

**如何验证？**

已有 [memory.test.mjs](../../../test/memory.test.mjs) 构造 450 条后续事件，检查 200 条分页、旧快照仍可查询、项目隔离及 Unicode 字面搜索。本轮只阅读该测试，未重跑。

**迁移到猎必得：**记录谁基于哪个岗位版本给了什么匹配建议、顾问怎样修改、哪次操作推进了状态，方便复盘和反馈归因。这是迁移设想。

## 6. ApiX 亮点二：统一异构 CLI 运行时

### 6.1 面试先说这段

> 多种编码 CLI 的启动方式、事件和结束语义不同。ApiX 把命令定位、参数构建、事件处理和用量采集分开，统一形成任务运行记录。判断成功不能只看进程退出码，还要看协议是否报告失败或完成；没有上报的 Token 用量保留未知。

### 6.2 实现分工

| 模块 | 实际职责 |
| --- | --- |
| [runtime-adapters.ts](../../../src/runtime-adapters.ts) | 找可执行入口、登记能力、构造 CLI 参数、自定义适配器 |
| [control-plane.mjs](../../../control-plane.mjs) 的 `launch/handleNative` | 子进程、stdin/stdout、原生事件与最终状态 |
| [worker-events.ts](../../../src/worker-events.ts) | 部分运行时文本、失败标志及追加/覆盖语义归一化 |
| [employee-insights.ts](../../../src/employee-insights.ts) | 从已知事件提取 Token 用量，保存来源与覆盖范围 |

当前内置目录包括 Pi、Codex、Claude、Gemini、OpenCode、Kimi；它们不是六份完全相同的适配器接口，部分处理保留在宿主分支中。

### 6.3 五个可展开的代码细节

**一是入口解析。**优先读取运行时入口环境变量，再查自定义适配器或 PATH；JavaScript 入口通过当前 Node 解释器启动。Windows npm `.cmd` shim 会按包清单找真实 bin 入口，避免直接靠 shell 拼接命令。

**二是参数与任务输入分离。**使用 `spawn(executable, args, ...)`，以参数数组传递选项。Pi 通过 stdin 写 JSON RPC prompt；其他运行时按各自 CLI 接口传入任务。参数数组减少 shell 拼接风险，但员工仍可能具备 Bash 工具，不能因此宣称没有命令执行风险。

**三是 stdout 逐行缓冲。**一次 data 回调不一定是完整 JSON；先累积 buffer，遇到换行再解析，保留剩余片段。非法行记 `unparsed_stdout`；关闭时尾部内容记 `trailing_stdout`，不声称所有无换行尾 JSON 都已处理成事件。

**四是追加与覆盖分开。**Gemini/Kimi 的文本可能是增量，也可能是完整快照，`textMode` 决定 append 或 replace，避免重复拼接。

**五是成功判定分层。**进程非零退出、结构化终止错误、Pi 没有正常结束信号等都会影响结果。Codex 形如 `Reconnecting... n/n` 的特定诊断不会立即当作终态失败，随后仍看真实结束结果；不是忽略所有 error。

### 6.4 用量采集追问

- Pi 从 assistant `message_end` 中读取 usage，按消息累加。
- Codex 从 `turn.completed` 读取 usage；Claude/Kimi/Gemini读取相应结果事件，当前路径按报告值更新。
- OpenCode 按 `step_finish` 的用量累加。
- 统计保存 `input/output/cached` 及来源；覆盖率用 measuredRuns/totalRuns 表达。
- 不同 CLI/版本字段及累计口径可能变化。当前映射不等于通用且永久正确的计费标准，Token 也不自动等于实际账单费用。

**如何验证？**已有 [collaboration.test.mjs](../../../test/collaboration.test.mjs) 覆盖重连诊断与终态错误区分；[coordinator.test.mjs](../../../test/coordinator.test.mjs) 有结构化失败但退出码为零、用量、不同运行时等场景。模拟 CLI 与真实 CLI 联调要分别说明。

**迁移到猎必得：**MCP 工具也要区分调用成功、业务成功、任务完成，规范错误与观测；当前 CLI 适配本身不是 MCP。

## 7. ApiX 亮点三：版本绑定的权限与需求并发控制

### 7.1 面试先说这段

> 我关注“批准时允许，执行时已经不允许”的问题。ApiX 对管理者和员工分别存权限及版本，授权记录绑定双方版本，执行前重新核对。同时需求用 revision 防止旧请求覆盖新需求。权限版本、需求版本和计划标识各自解决不同的过期问题。

### 7.2 权限数据结构与规则

证据：[permissions.ts](../../../src/permissions.ts)。

- `apix_policies`：主键为 `(project_id, subject)`，subject 可以是管理者或员工，保存 mode、version。
- `apix_grants`：按 task 保存 project、employee、manager_version、employee_version、授权来源。
- 未配置时默认 `ask_approval`、版本 0。
- 任一方 `read_only`，任务启动决策为 deny；双方 `full_access` 为 allow；其余为 ask。
- `save()` 检查提交的 expectedVersion，再把版本加一；即使保存成同一种 mode，版本变化也会使旧授权失效。
- `grant()` 区分用户批准和策略授权，策略授权只能在双方允许时产生。
- `assertGranted()` 核对任务授权所属项目、员工、双方当前版本，以及是否已被 deny。

**源码逻辑的简化表达，不是新增实现：**

```text
执行允许 = 授权存在
        且 项目和员工匹配
        且 管理者当前版本 == 授权绑定版本
        且 员工当前版本 == 授权绑定版本
        且 当前决策不是 deny
```

### 7.3 revision 如何处理异步返回

证据：`coordinator.ts` 的 `editable/discuss/assertExecution`。

1. 前端提交当前 revision；`editable()` 检查是否忙、版本是否一致。
2. 模型推理前记录用户交互；耗时推理在事务外执行，避免在等待模型时持有整个业务事务。
3. 推理返回后重新检查 revision，拒绝过期结果。
4. 可修改需求更新时递增 revision；已确认需求还与计划 brief 绑定。
5. `launch()` 调用 `assertExecution()`，再次检查运行会话、计划、confirmed_revision 与执行授权。

### 7.4 追问中要讲清的边界

**这是不是分布式乐观锁？**

当前主要是单进程控制面内的版本校验和同步数据库操作，不能直接宣称支持多副本竞争。多进程写入需进一步使用带版本条件的 SQL 更新、检查受影响行数、事务及运行唯一性约束。

**busy、revision、权限版本有何区别？**

busy 是进程内避免同会话重复处理；revision 发现业务内容过期；权限版本发现执行资格变化。busy 重启就消失，不能代替持久化版本。

**撤权就能立即停止所有操作吗？**

系统会使旧授权失效并请求停止相关运行，但已经发生的文件写入不自动撤销，外部子进程也不保证全部立即结束。

**如何验证？**既有 coordinator 测试覆盖员工单独授权、撤权后执行拒绝、推理期间授权变化等。讲“代码有对应测试”，不要在没重跑时讲“今天已全量通过”。

**迁移到猎必得：**将推进批准绑定申请对象、目标状态、操作者和版本。服务端授权不能采信模型参数里的角色或 approved 标记。

## 8. ApiX 亮点四：DAG、并发准入和 Git 交接

### 8.1 面试先说这段

> 并发协作需要同时解决执行顺序和代码一致性。ApiX 在计划阶段约束依赖只引用前序步骤，执行阶段检查前置是否已验收、并发和预算是否允许。员工用独立 worktree，验收时计算差异指纹并冻结代码，下游应用已验收交付；冲突会阻止启动。

### 8.2 计划与调度

证据：[coordinator.ts](../../../src/coordinator.ts)、[task-scheduler.mjs](../../../src/task-scheduler.mjs)、[execution-control.mjs](../../../src/execution-control.mjs)。

1. 计划步骤通过员工存在性、prompt、dependsOn 等校验。
2. 第 i 步的依赖索引必须满足 `0 <= dependency < i`。这个约束让模型按已有拓扑顺序表达计划，阻止自依赖及向后依赖，不是任意图的 Kahn 排序。
3. 数据库用 `task_dependencies` 保存 Task 间边。
4. 调度器处理 queued/awaiting_approval：先看失败依赖，再看批准，接着检查依赖完成门槛及准入。
5. 协调和协作计划要求前置 `accepted`；部分旧流程允许 `completed/accepted`，不能说全系统所有模式都相同。
6. 默认项目并发 4、同员工在本项目并发 1；running、stopping、unknown 都计入占用。unknown 仍可能有旧进程，不能重启就当额度释放。
7. `pump()` 有进程内重入保护。准入与真正创建运行还要走宿主检查，不能把这个布尔标记说成分布式调度锁。
8. 前置失败、取消、未知、待修改等状态可将下游置为 blocked，并继续检查下游依赖。

### 8.3 冻结交付的真实实现

证据：[code-handoffs.mjs](../../../src/code-handoffs.mjs)。

1. 校验工作区是否为本任务的托管路径，核对真实路径、Git 根、公共目录及 worktree 登记，避免指向其他目录或仓库。
2. 检查未解决冲突。
3. 用临时 `GIT_INDEX_FILE` 构建包含修改、删除、新文件的 tree，保留员工原 index。
4. 对 `head:inputCommit:tree` 计算 SHA-256 指纹。tree 标识具体文件内容，inputCommit 标识本任务基于什么输入。
5. 验收时重查指纹；用 `git commit-tree` 创建交付提交，并用 `refs/apix/deliveries/...` 保留引用。
6. 下游按依赖祖先顺序取得 accepted 交付，计算各任务输入到冻结提交的二进制 diff，通过 `git apply --3way --index` 应用。
7. 生成下游输入提交并记录 handoff 来源。仓库或基线不一致、三方应用冲突时保留现场，返回 `HANDOFF_CONFLICT`。

### 8.4 常见追问

**为什么不只看员工回复“已完成”？**回复不能证明磁盘代码、依赖交接或验收条件满足。

**为什么不用同目录加文件锁？**worktree 从目录上分开修改；协作租约要求参与方遵守，外部 CLI 不一定检查。worktree 仍不能隔离网络、系统资源或阻止越界访问。

**指纹意味着验收内容绝对不会变化吗？**它检测检查时点的内容变化；冻结提交提供稳定交付引用。外部进程继续写文件、检查期间竞态和源仓库集成仍需控制，不能说有哈希就消灭一切竞态。

**当前自动合并源仓库吗？**不因员工完成而自动合并。任务交接、最终集成和源仓库应用是不同步骤。

## 9. ApiX 亮点五：Mailbox、幂等与租约锁

### 9.1 面试先说这段

> Mailbox 把指导和结果从临时文本变成可追踪消息。每条消息有项目、发送者、接收者、关联 ID 和幂等键，状态持久化到 SQLite。运行凭据还绑定具体任务与 Run，避免同员工并发时串收消息。它支持重投递和重试，但不保证业务副作用 exactly-once。

### 9.2 消息的三个标识

| 字段 | 作用 |
| --- | --- |
| message ID | 某条具体消息 |
| correlation ID / replyTo | 请求与回复的关联链 |
| idempotency key | 重复发送时识别同一意图，防止重复入队 |

幂等处理不只检查 key：`sendMessage()` 在同项目找到已有 key 后，还比较发送者、接收者、类型、payload、回复对象以及任务/运行字段。同 key 同内容返回 duplicate，同 key 不同消息拒绝。

### 9.3 状态与重试

```text
queued → delivered → processing → completed
                       ↓ nack
                  queued 或 failed
其他结束路径：expired / rejected
```

- 未 ack 的 delivered 消息可再次领取，所以接收端仍要防重复处理。
- ack 记录 attempt；nack 在允许次数内重新排队。
- 当前退避为 `min(60000, 1000 * 2 ** retry_count)` 毫秒，没有随机 jitter；不要说已经实现带抖动退避。
- 过期检查在相关读取或操作路径触发，不等于有实时精确到毫秒的独立调度器。
- 员工必须实际轮询邮箱才能收到指导；记录发送成功不能证明员工已采纳。

### 9.4 凭据与租约

`agent-mailbox.ts` 使用 32 字节随机值生成短期令牌，数据库保存 SHA-256 哈希。认证 JOIN Run 和 Task，校验活动状态及项目、员工绑定；运行结束或重启转 unknown 后不能继续用旧令牌。新运行不重放旧指导。

`agent_locks` 保存资源类型、key、持有者、租约标识与过期时间，支持续租和释放。续租检查持有者与过期状态，管理者可释放。它是应用内协作锁，不是可约束所有文件写入的强制锁，也没有让外部写入方验证 fencing token 的完整机制。

源码：[mailbox.mjs](../../../src/mailbox.mjs)、[agent-mailbox.ts](../../../src/agent-mailbox.ts)。既有验证：[messaging.test.mjs](../../../test/messaging.test.mjs) 与 coordinator 的并发 Run 邮箱隔离场景。

**迁移到猎必得：**用关联 ID 串起推荐请求与反馈；对候选人推进写操作，在业务事务层实现幂等。不能只靠消息不重复入队就宣称不重复推进。

## 11. MewCode 亮点一：MCP 接入及内部工具适配

### 11.1 面试先说这段

> 当前实现是 MCP 客户端接入。连接层负责 stdio 或 Streamable HTTP 与会话生命周期，管理器连接多个 Server 并发现工具，Wrapper 再把外部工具映射到内部 ToolRegistry。这样 Agent 可以沿用工具执行流程，不需要为每个外部服务单独写模型调用逻辑。这不等于已经开发了生产级招聘 MCP Server。

### 11.2 一次调用如何走通

```text
TUI 加载 MCP 配置
  → MCPManager.register_all_tools
  → MCPClient.connect
  → stdio_client 或 streamable_http_client
  → ClientSession 初始化（当前代码所用 SDK 调用方式）
  → list_tools 发现工具
  → MCPToolWrapper → ToolRegistry
  → ToolSearch 发现后暴露给模型
  → 模型给出工具名与参数
  → Wrapper.execute → Client.call_tool
  → ToolResult 回到 Agent 工具循环
```

### 11.3 四个具体实现点

1. `AsyncExitStack` 管理传输、会话、HTTP 客户端等异步上下文，关闭时逆序释放；连接失败也进入清理路径。
2. stdio 使用 `StdioServerParameters`，子进程环境通过 `build_child_env` 构造；HTTP 路径解析配置请求头中的环境变量，再创建 `httpx.AsyncClient`。这里只能证明配置式请求头接入，不是完整 OAuth 授权实现。
3. 工具名为 `mcp_{server_name}_{tool_name}`，原始工具名保留用于远端调用；description 和原始 inputSchema 供模型使用。
4. 工具默认 `should_defer=True`，需通过 ToolSearch 发现；`is_concurrency_safe=False` 是本实现的保守执行策略，不是 MCP 协议禁止并发。

### 11.4 追问时最容易说过头的地方

**Schema 是不是完整校验？**

`_build_params_model()` 当前只映射顶层 properties 的基本类型和 required，支持 string/integer/number/boolean/object/array。没有完整落实 enum、嵌套字段、oneOf、items 等 JSON Schema 约束。`get_schema()` 保留原 schema，不代表本地 Pydantic 校验已经等价实现所有语义。

**工具返回什么？**

Wrapper 提取文本、用 MIME 描述图像、提取嵌入文本资源；把 `isError` 映射为内部错误标记。没有完整保留图片和结构化结果语义，不能称为无损通用结果适配。

**断线自动重试了吗？**

调用异常会将 client 标记非存活并返回错误；下一次 execute 发现该状态时尝试 connect。本次失败调用不会被透明安全重放，is_alive 也不是主动健康探测。Manager 另有重建客户端路径，但 Wrapper 持有自己的引用，不能笼统称为所有路径自动同步换连接。

**多个 Server 有一个失败会怎样？**

注册循环按 Server 捕获异常并返回错误列表，继续处理其他 Server。还需要考虑工具发现失败后的资源清理和重复注册等情况，不能只凭局部容错就声称完全健壮。

**为什么对猎必得有帮助？**

这说明你理解 MCP 如何接进 Agent。但招聘写工具还需补业务授权、状态机、幂等、错误分类、完整 Schema、结果查询和评测；这些属于后续设计，不能说当前已经具备。

## 12. MewCode 亮点二：DAG 校验与批次并行

### 12.1 面试先说这段

> MewCode 把任务表达为有依赖的节点，创建时检查 ID 唯一、依赖存在及无环。运行时每轮取依赖全部完成的 ready 节点，在并发上限内用 asyncio 执行，并把前置结果传给下游。失败节点会影响依赖链，避免明知前置失败还继续做无效工作。

### 12.2 数据与算法

- `DAGNode`：id、task、dependencies、agent_type、max_attempts、status、result、error 等。
- `DAGRun`：节点字典、整体状态、时间和错误。
- `validate()` 复制每个节点的依赖集合，每轮移除没有依赖的节点，再从其他集合删除这些 ID；如果还有节点但没有 ready，就有环。这是 Kahn 思路的集合实现。
- 当前反复扫描剩余节点及集合，不应直接说是用邻接表和入度队列实现的 O(V+E)。若要优化，才考虑邻接表、入度和队列。
- 每轮 ready 数量限制为 max_parallel，`asyncio.create_task` 后用 `gather(return_exceptions=True)` 等整批结束。
- 下游上下文是 `dependency ID → 前置输出字符串`，不等于代码已通过 Git 合并进工作区。
- `_run_node()` 支持有限重试，节点重试退避上限 4 秒。

### 12.3 面试官可能追问的取舍

**一个快任务完成后立即补位吗？**

当前是批次屏障：等待该批全部结束后再取下一批，不是持续补位的工作池。优点是简单，缺点是快节点会等慢节点；如业务需要可改成完成一个调度一个。

**fail_fast 是瞬时中断吗？**

不是。当前先等 gather 收集本批结果，再处理失败；fail_fast 会阻塞仍 pending 的节点并返回失败，不等于一有错误就杀掉本批其他任务。

**fail_fast=False 呢？**

允许无关分支继续，依赖失败/阻塞/取消的节点标为 blocked。业务上要区分“全图停止”和“只阻断依赖链”。

**单次任务失败可以无条件重试吗？**

代码有重试能力，但外部写操作是否可重放仍依赖业务幂等。不能把“再次调用 executor”当作已解决所有副作用问题。

源码：[dag.py](E:/Projects/wyy/Mewcode/mewcode/runtime/dag.py)。既有 [test_runtime.py](E:/Projects/wyy/Mewcode/tests/test_runtime.py) 有环检测、两前置并行及下游结果传递场景。

## 13. MewCode 亮点三：快照、事件日志与恢复

### 13.1 面试先说这段

> Runtime 把最新运行状态保存成 JSON 快照，把过程事件追加到 JSONL。快照先写临时文件再 replace，减少半写入损坏原快照的问题；RunStore 用同实例内 RLock 协调线程写入。恢复时读取未结束的 Run 并重新调度，不是继续原来的协程执行位置。

### 13.2 存储的真实步骤

```text
save(run)
  → 序列化 Run
  → 进入同实例 RLock
  → 写 {run_id}.json.tmp
  → replace 为 {run_id}.json

append_event(run_id)
  → 进入同实例 RLock
  → 读取历史，计算该 Run 的下一 sequence
  → 追加一行 JSONL 并 flush
```

**必须知道的限制：**

- RLock 是线程锁，不是多进程文件锁，不保证多个 RunStore 实例共同写同目录安全。
- replace 侧重避免读到半份目标快照，不等于断电后所有数据必然持久化；代码的 flush 不能等同于 fsync。
- 快照与事件是两个文件，没有跨文件事务，崩溃时可能不完全一致。
- 事件序号读取实现会读整个日志再取最后一行，不是真正 O(1) 随机读尾部；长日志需要优化。
- 读取会跳过损坏事件行，这利于容错，但不代表保有完整、不可缺失的审计轨迹。
- DAG 自己的 `_save()` 也使用临时文件 replace，但不能把 RunStore 的 RLock 保证套到 DAG 存储上。

### 13.3 recover 到底恢复了什么

`AgentRuntime.recover()` 扫描快照，只处理 pending/running；有 agent_factory 才能重新调度。它改成 pending、保存、发 run_recovered，然后创建新的执行协程。

对话恢复交给 conversation_factory；外部工具副作用不能自动回滚或精确续接。attempt/max_attempts 也会影响是否真正进入下一轮：若快照已经用尽尝试次数，不能承诺 recover 一定继续完成。这个边界需要额外测试与恢复策略。

**与 ApiX 对比：**MewCode 倾向重新调度；ApiX 对旧 CLI 进程采取 unknown 和人工检查。两者控制的运行对象不同，不能用同一个“断点续跑”概括。

## 14. MewCode 亮点四：Runtime 服务化与 SSE

### 14.1 面试先说这段

### 14.2 接口与生命周期

| 接口 | 当前作用 |
| --- | --- |
| `POST /v1/runs` | 返回 202 与运行记录，后台创建 asyncio Task |
| `GET /v1/runs/{id}` | 查询快照中的状态和结果 |

| 消息幂等和关联 | 重复推进、超时后不知道是否成功 | 把操作 ID、幂等与结果查询落实到业务服务 |
| 状态与事件记录 | 为什么推荐、谁改过、反馈怎样追踪 | 保留证据、版本、操作者和结果，支持归因 |
| DAG 与有限重试 | 多步骤查询分析及执行 | 只让必要步骤自动化，独立只读步骤可并行 |
| 用量观测 | AI 提效是否划算 | 看单位成功任务成本，不只看 Token 减少 |

这些是能力迁移建议，不代表已经做过招聘系统。RAG 负责支持检索和证据分析；MCP 负责能力接入；业务服务负责权限、状态和一致性。不要将三者混为一个“智能体功能”。

## 18. 面试官最可能追问的 12 题

1. **你个人负责哪部分？**给模块、个人动作、证据和限制；不以仓库功能列表代替职责。
2. **为何要两个项目？**从单 Agent 工具循环到多 CLI 协作治理，分别讲清边界。
3. **事件溯源和日志有什么区别？**讲数据模型和使用方式，再准确限定当前快照查询能力。
4. **两个人同时改需求怎么处理？**revision 校验；解释当前单进程约束，别冒称分布式 CAS。
5. **权限撤销后呢？**旧授权拒绝、请求停止；外部副作用另行处理。
6. **DAG 怎么查环？**MewCode 集合式 Kahn；ApiX 前序索引约束与交接时的循环防御。
7. **并发任务怎样不互相覆盖？**worktree、范围和验收交接；不能保证没有逻辑冲突。
8. **MCP 工具校验完整吗？**原 schema 保留，本地转换不完整，举 enum/嵌套限制。
9. **工具超时是否重试？**先分错误和副作用，写入结果未知先查询，不盲重放。
10. **recover 是接着执行吗？**新协程重新调度，attempt、上下文和副作用均需处理。
11. **测过什么？**区分本轮阅读的测试、自己真实跑过的测试和真实模型联调。
12. **AI 写代码，你有什么能力？**拿一个真实设计/定位/修正/验证案例回答。

## 19. 面试前 90 分钟练习安排

| 时间 | 动作 | 达成标准 |
| --- | --- | --- |
| 0–10 分钟 | 自我介绍 + 两项目区分 | 不超过约定时长，个人职责明确 |
| 10–30 分钟 | ApiX 权限版本与执行链 | 能指到函数，解释一个失败路径 |
| 30–50 分钟 | MewCode MCP 与 Runtime | 画出调用链，讲清装配和恢复边界 |
| 50–65 分钟 | DAG、worktree 和交付 | 不混讲算法、验收、消息与代码 |
| 65–80 分钟 | 选两个故事自问自答 | 每段有个人动作、验证和反思 |
| 80–90 分钟 | 映射猎必得及反问 | 能提出一个小闭环方案及验收指标 |

最后在纸上填好：我负责什么；我解决的一个真实问题；为何没选替代方案；怎么证明有效；现在还有什么限制。填不出来的点先不要当成主打亮点。
