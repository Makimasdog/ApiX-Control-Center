# 员工失败恢复与主会话监督

更新：2026-10-31。实现入口为 `workflow-recovery.mjs`、`autonomy.ts`、`coordinator.ts` 与 `assistant-loop.ts`。这是对既有有限自动恢复的补齐，不是无限重试。

## 处理流程

员工失败 → 宿主判断是否允许自动恢复 → 在原授权员工中选择可用员工 → 保留已有工作区，携带原需求与真实失败诊断安排修复 → 重新检查/验收 → 释放后续依赖 → 主会话继续。

普通自动协作最多自动修复 2 次，首次恢复起最多 30 分钟；自主交付沿用项目的 maxRepairs 和目标时间限制。恢复仍受员工能力、预算、资源、需求版本和任务授权约束；原进程未确认结束、未知外部副作用及代码交接冲突不自动重跑。修复后执行完成不等于验收通过，后续依赖仍须等待前置任务 accepted。

本轮修复了两个状态衔接问题：

- 普通协作中，异常任务全部是仍满足自动恢复条件的 failed 时，整体显示 queued，表示等待自动处理；不是直接认定需要人工介入。unknown、cancelled、rejected、blocked、待审批等状态不会被这一规则掩盖。
- 子流程仍为 running/queued 时，模型返回 finish blocked 不再让主会话提前退出监督。主会话保持 waiting_agents；员工完成并全部验收后继续主循环。真正无法继续的子流程仍转 attention，并在主对话显示处理入口。

既有重启、授权、停止、预算、幂等和恢复检查不变；本轮不自动解除已有 attention，不自动批准验收、不初始化用户 Git 仓库。

## 诊断与界面

协调会话 details 的每个任务增加可为空的 recovery：state、automatic、attempts、maxAttempts、reason。它读取持久恢复记录和当前准入条件，不写入恢复状态；automatic 仅表示当前普通协作具备自动恢复资格，不代表员工已经启动。自主交付仍使用原 autonomy.tasks/repairs/reason。

主会话的子流程观测补充脱敏 failure（最多 2000 字符）与 recovery。普通自动修复指令携带最近的实际失败诊断（脱敏后最多 2000 字符），作为待核实证据，不授予新权限。

工作台员工行显示“等待自动修复”“自动修复中（已尝试/上限）”、失败原因和不能自动处理的原因；公开文本经过 html.ts 转义。详细原始事件、验收及人工恢复仍从既有 Run/协作进度入口查看。

supervision_waiting 只用于主会话展示提示，从标准和稳定布局模型历史中排除；delegation_blocked 是终态监督事实，稳定布局保留，避免遇到未知事件中止投影。原始日志不删除。

## 不能自动消除的失败

| 情况 | 处理 |
| --- | --- |
| 已知执行/验证失败且当前授权、进程和工作区满足恢复条件 | 有限自动修复；优先已授权的空闲替代员工 |
| 所有合适员工暂时占用 | 等待资源，不消耗修复次数 |
| 已达到次数/时间上限 | 暂停，展示原因，检查后人工恢复 |
| 认证、额度、配置、结果未知或交接冲突 | 保留相应处理要求，不以重试掩盖问题 |
| “计划任务要求 Git 项目以创建独立 worktree” | 新失败归为项目准备/配置问题；检查登记的项目根目录和 Git 状态，不反复派员工解决启动前条件 |

历史错误不证明项目当前仍有同一问题；已暂停的历史任务不因升级自动重开，也不追改旧故障记录。

## 验证与限制

复现：`node --test test/workflow-recovery.test.mjs test/workflow-recovery-http.test.mjs test/assistant-loop.test.mjs test/autonomy.test.mjs test/fault-policy.test.mjs test/prompt-projection.test.mjs`，以及 `npm run test:ui:agents`、build/check。

实际 HTTP 夹具验证了员工失败、自动改派、已有文件保留、修复携带失败原因、前置验收后 DAG 继续；主循环测试验证等待恢复时不会提前 attention，以及重建服务后重新接回完成流程。浏览器覆盖恢复文案和失败文本转义。均未调用付费模型。

本轮不覆盖全部异常类型、真实供应商故障或成品桌面安装包；没有运行全量测试或远程 CI。详细范围见 [本轮 Codex 自审](../../协作/审查/2026-10/2026-10-31-员工失败恢复与监督衔接自审.md)。
