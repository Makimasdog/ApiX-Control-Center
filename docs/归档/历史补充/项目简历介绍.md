# ApiX-Control-Center 项目简历介绍

## 项目概述

**项目名称**: ApiX Control Center\
**项目类型**: AI Agent 管理与协调平台\
**技术栈**: Node.js 22.19+, TypeScript, SQLite, SSE, 原生前端\
**版本**: 0.1.0\
**许可证**: MIT

---

## 项目定位

ApiX 不是又一个编码 Agent，而是**管理 Agent 的管理者 Agent**。

在 AI 编码工具爆发的时代，开发者面临新问题：如何协调多个 AI 员工（Pi、Codex、Claude Code 等）高效协作？ApiX 解决这个问题——它与用户澄清需求、规划任务、分派工作、监督进度、收集交付物，让多个 AI 员工像真实团队一样协同工作。

**核心理念**：用户是决策者，ApiX 是管理者，AI 员工是执行者。ApiX 不直接产出代码，而是确保正确的人做正确的事。

## 核心技术能力

### 1. 多 Agent 协调系统

**问题**：不同 AI 工具有不同的接口、权限和输出格式，手动协调成本高。

**解决方案**：统一的运行时适配器层，屏蔽底层差异。

- **内置支持**：Pi RPC、Codex JSONL、Claude stream-json
- **自定义扩展**：登记任意可执行文件作为员工运行时
- **状态观测**：统一的员工能力发现、进度采集、取消控制
- **Git worktree 隔离**：并行任务采用独立工作区，避免冲突

```typescript
// 运行时适配器示例
interface AgentCapabilities {
  id: string;
  name: string;
  available: boolean;
  managed: boolean;
  observable: boolean;
  cancellable: boolean;
  stateSource: string; // 'Pi RPC' | 'Codex JSONL' | 'Claude stream-json' | '自定义'
}
```

### 2. 五维需求工程

**问题**：用户模糊的需求直接交给 AI 执行，往往产出偏离预期。

**解决方案**：强制五维需求完整度检查，确保需求可执行、可验收。

五个必填字段：
- **目标**：要解决什么问题，最终改变什么？
- **范围与边界**：包含什么，不包含什么？
- **约束**：技术、时间、权限限制
- **交付物**：可检查的具体成果
- **验收标准**：通过什么检查才算完成？

```typescript
// 需求评估
interface RequirementAssessment {
  score: number;        // 完整度 0-1
  threshold: number;    // 阈值
  missing: RequirementField[];  // 缺失字段
  conflicts: string[];  // 冲突项
  ready: boolean;       // 是否可执行
}
```

**关键设计**：模型生成的完整度评估不能替代用户确认。只有用户明确确认版本后，需求才进入计划阶段。

### 3. 双模式交互系统

**对话模式**：自然沟通，ApiX 从用户表达中整理需求，不强迫按表单顺序回答。适合探索性需求。

**约束模式**：逐项检查五个字段，优先追问缺失或冲突项。适合明确边界的需求。

两种模式共享同一确认门槛——五项需求完整且无冲突，用户确认后才进入计划。

```typescript
// SSE 实时推送澄清问题
POST /api/coordination/sessions/{id}/discuss
Content-Type: text/event-stream

data: {"question":"你希望这次重构包含哪些模块？"}
data: {"question":"性能约束是什么？"}
```

### 4. 三级权限体系

**问题**：AI 员工权限过大存在风险，过小又影响效率。

**解决方案**：按项目和主体（ApiX 或员工）独立设置权限。

- **完全访问** (full_access)：跳过审批，适合受信任的环境
- **请求批准** (ask_approval)：计划需用户批准，执行不逐个拦截
- **只读** (read_only)：只能查看，不能执行

```typescript
// 权限决策逻辑
function decision(projectId, employeeId): 'allow' | 'ask' | 'deny' {
  const modes = [get(projectId).mode, get(projectId, employeeId).mode];
  return modes.includes('read_only') ? 'deny'
       : modes.every(m => m === 'full_access') ? 'allow'
       : 'ask';
}
```

**关键设计**：任务授权绑定双方权限版本。收回权限时，旧授权自动失效。

### 5. 事件溯源账本

**问题**：多 Agent 协作状态复杂，难以追溯决策过程。

**解决方案**：所有状态变化写入事件账本，支持任意时刻状态回放。

```typescript
// 事件结构
interface DomainEvent {
  sequence: number;      // 全局递增序号
  projectId: string;
  aggregateId: string;   // 聚合根 ID
  kind: string;          // 事件类型
  actor: string;         // 行为主体
  payload: unknown;
  createdAt: string;
}

// 事件类型示例
'coordination.snapshot'   // 状态快照
'interaction.recorded'    // 交互记录
'permission.changed'      // 权限变更
'execution.authorized'    // 执行授权
```

**能力**：
- 事件序号回放：重建任意时刻状态
- 关键词检索：搜索历史事件
- 跨目标参考：已确认的历史需求可作为新目标的参考

### 6. 实时监督与指导

**问题**：员工执行过程中，管理者难以及时介入。

**解决方案**：Mailbox 消息系统 + 主动监督逻辑。

- **员工上报进度**：通过 mailbox 发送进度报告
- **ApiX 主动请求**：长时间无报告时，主动请求进度
- **指导决策**：根据进度选择指导重点（范围、验收、依赖、交付）
- **用户补充**：用户可在目标工作台向运行中的员工补充说明

```typescript
// ApiX 指导决策
type GuideAction = 'guide' | 'escalate' | 'observe';
type GuideFocus = 'scope' | 'verification' | 'dependencies' | 'delivery';

// 指导逻辑
if (report.blocked) {
  return { action: 'escalate', focus: 'verification' };
} else if (needsGuidance) {
  return { action: 'guide', focus: selectedFocus };
} else {
  return { action: 'observe', focus: 'verification' };
}
```

### 7. Token 用量追踪

**问题**：多员工协作时，难以统计真实成本。

**解决方案**：从各运行时采集真实 Token 用量，不编造数据。

- **Pi**：从 RPC 消息的 usage 字段累加
- **Codex**：从 turn.completed 事件提取
- **Claude**：从 result 事件提取
- **未报告**：显示"未知"，不虚构数据

```typescript
// 用量采集
interface Usage {
  input: number;
  output: number;
  cached: number;
  source: string; // 'pi-rpc' | 'codex-jsonl' | 'claude-stream'
}
```

## 关键技术亮点

### 1. 类型安全的 TypeScript 迁移

新核心模块（coordinator、apix-agent、contracts、permissions、memory 等）使用严格 TypeScript，编译产物 dist/ 不入库。旧 HTTP/SQLite/进程托管保留 JavaScript，按边界逐步迁移。

```typescript
// 严格的类型定义
type PermissionMode = 'full_access' | 'ask_approval' | 'read_only';
type InteractionMode = 'structured' | 'conversational';
type RequirementField = 'goal' | 'scope' | 'constraints' | 'deliverable' | 'acceptance';
```

### 2. 事件溯源与状态回放

所有状态变化写入事件账本，支持：
- 任意时刻状态重建
- 关键词检索历史事件
- 跨目标参考已确认需求

```typescript
// 状态回放
function stateAt(projectId, aggregateId, atSequence?) {
  const history = events(projectId, aggregateId, atSequence);
  const snapshot = [...history].reverse()
    .find(e => e.kind === 'coordination.snapshot');
  return { atSequence, state: snapshot?.payload ?? null, events: history };
}
```

### 3. SSE 实时推送

目标对话使用 POST SSE 流，逐步展示模型生成的澄清问题。流结束后以经过校验并保存的正式会话记录为准。

```typescript
// SSE 推送澄清问题
response.writeHead(200, {
  'Content-Type': 'text/event-stream',
  'Cache-Control': 'no-cache, no-store',
  'Connection': 'keep-alive'
});

for (const event of initial) {
  response.write(`id: ${event.id}\nevent: ${event.event_type}\ndata: ${JSON.stringify(event)}\n\n`);
}
```

### 4. 幂等消息与租约锁

Mailbox 系统支持：
- 请求/回复关联
- 幂等冲突检查
- 超时/重试机制
- 交付物引用
- 监督拦截
- 租约锁防止并发冲突

### 5. Git Worktree 隔离

并行任务采用独立 worktree，避免员工之间的文件冲突。计划工作区与主仓库隔离，完成后由用户检查集成。

## 使用场景

### 场景 1：多模块重构

**需求**：重构一个大型项目的认证模块、数据库层和 API 接口。

**ApiX 工作流**：
1. 与用户澄清：重构范围、约束（不破坏现有功能）、交付物（重构后的代码 + 测试）、验收标准（所有测试通过）
2. 生成计划：
   - 步骤 1：Pi 员工分析现有代码结构
   - 步骤 2：Codex 重构认证模块
   - 步骤 3：Claude 重构数据库层
   - 步骤 4：Pi 员工重构 API 接口
   - 步骤 5：Codex 编写集成测试
3. 分派任务：每个员工在独立 worktree 工作
4. 监督进度：ApiX 主动请求进度，根据报告选择指导重点
5. 收集交付物：验收每个步骤的输出

### 场景 2：跨团队协作

**需求**：前端团队和后端团队协同开发新功能。

**ApiX 工作流**：
1. 注册员工：前端员工（Pi）、后端员工（Codex）
2. 澄清需求：API 接口规范、数据格式、交付物（前端组件 + 后端 API）
3. 生成计划：
   - 步骤 1：后端员工设计并实现 API
   - 步骤 2：前端员工基于 API 开发组件
   - 步骤 3：后端员工编写 API 测试
   - 步骤 4：前端员工编写组件测试
4. 依赖管理：步骤 2 依赖步骤 1 完成
5. 监督执行：ApiX 检查依赖关系，确保顺序执行

### 场景 3：探索性需求

**需求**：用户有一个模糊的想法，想探索可行性。

**ApiX 工作流**：
1. 对话模式：自然沟通，ApiX 从用户表达中整理需求
2. 逐步澄清：目标是什么？范围多大？有什么约束？
3. 需求完整度检查：五项字段覆盖率可视化
4. 用户确认：补全所有字段后，用户确认版本
5. 生成计划：基于确认的需求生成可执行计划

## 与 Pi 的关系

ApiX 使用 Pi 作为推理底座，但两者职责清晰分离：

- **Pi**：提供 LLM 推理能力，是技术底座
- **ApiX**：管理者 Agent，负责沟通、规划、监督
- **Pi 员工**：执行者，与 ApiX 有独立身份和权限

ApiX 不直接产出代码，而是通过 Pi 推理生成沟通内容、需求摘要和任务规划。员工在 Pi 员工执行任务时，ApiX 监督进度并提供指导。

## 总结

ApiX-Control-Center 是一个设计精良的 AI Agent 管理平台，解决了多 Agent 协作的核心问题：

1. **需求工程**：五维需求模型确保需求质量
2. **多运行时协调**：统一管理 Pi、Codex、Claude 等工具
3. **权限治理**：三级权限体系平衡安全与效率
4. **事件溯源**：完整的状态变化历史，可追溯、可回放
5. **实时监督**：SSE 推送进度，主动指导员工

项目的技术深度体现在：

- **类型安全**：严格 TypeScript，逐步迁移旧代码
- **事件驱动**：所有状态变化写入事件账本
- **实时通信**：SSE 推送澄清问题和进度更新
- **隔离执行**：Git worktree 隔离并行任务
- **幂等消息**：Mailbox 系统支持请求/回复关联和租约锁

ApiX 不是要替代 AI 编码工具，而是让它们更好地协同工作。它是 AI 时代的"项目经理"，确保正确的人做正确的事，交付正确的成果。
