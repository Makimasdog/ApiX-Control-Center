2026-11-24。来源：用户从使用者视角走查 ApiX，列出 19 条。本文只做**核实与分级**，不含实施方案。

核实基线：worktree `wonderful-turtle`，分支 `design-auto-bugfix-workflow`，HEAD `d9a5093`（= main + 设计文档 + 巡检脚本）。

## 先说一条被推翻的

**第 4 条的前提不成立。** 这条说「默认执行方式是自动执行」，实测不是：

- `src/coordination/permissions.ts:41` —— 无策略记录时返回 `{ mode: 'ask_approval' }`
- `web/assistant.ts:39`、`:368` —— 新建/切换对话时执行方式显式重置为 `ask_approval`

所以「第一句话就能改源项目」这个担心在当前代码里不成立。

但这条的**后半段是真的**：仓库确实没有会话级撤销。工具改完文件，错了只能靠 git 或手工还原。这是真问题，只是它不是「默认太危险」，而是「出事没退路」。

## 逐条核实证据

**1** 登录页要求手抄 token。可改为启动时打印一条带令牌的本地链接，或托盘菜单「复制登录链接」。桌面端自动连接已可用，缺的是 web/gateway 这条路径。

**3** 输入框上方没有当前项目名，只能靠左栏高亮推断。

**5** `web/assistant.ts:16` 是普通 `<select>`，三个选项平铺在折叠区附近，风险等级无视觉区分。

**6** `web/provider-center.ts:79`：卡片状态取自**本次页面内**的测试结果（`lastConnection`），没有测试就一律 `未验证连接`。而 `未绑定` 取自 agent 的 `providerId`，与「这个供应商是否真的在产出回答」是两件事。→ 应改为展示最近一次成功推理的时间与模型。

**9** `web/chat-history.ts:9` 的状态表把 `attention` 直接映射为「需检查」，但 attention 可能来自多种原因（服务重启中断 / 等待批准 / 检查失败），全部压成同一个词。

**10** 错误经 `safeError()` 后直接上屏，未包中文解释与上下文（命令、工作目录）。

**12** `src/infrastructure/environment.mjs:31` 确实调用 `process.loadEnvFile` 并兼容 `ali_api_key` 小写别名，所以**环境是读的**；缺的是界面上的「从 .env 导入到供应商配置」按钮。这一点比原描述轻。

**19** 已有素材：`code-handoffs` 的交付指纹与 diff、`assistant_events` 的工具事件。缺的是把它们按会话串成一条人话时间线。这是「加调度能力」之外的另一种信任来源，值得单列。
