# 02 · 三个主流程的页面级走查

每一步写明「在哪个屏 / 看到什么 / 下一步点哪里」。按钮文案为动词开头的现有或建议文案（现有文案已标注）。
涉及的现有模块用文件名标注，方便工程师直接定位实现。

## 2.1 流程一：提需求 → 交付审阅

| # | 屏 | 用户看到 | 下一步点 |
|---|---|---|---|
| 1 | 任意页，`Ctrl K` | 命令条：需求输入框（占位「描述你要做的事，例如：给能力中心加按来源筛选」）、当前项目、员工、执行方式、预算上限；底部提示 `↑↓ 选择 · Enter 确认 · Esc 关闭` | 输入需求，`Enter` |
| 2 | 命令条 → 参数确认 | 3 行摘要：项目 / 员工 / 预算上限（可改），`发起任务`（主）/ `取消` | 点 `发起任务` |
| 3 | 任务页（自动跳转 `#/tasks/t_7f3a`） | 粘性头部：任务标题、状态胶囊「起草契约」、项目、员工、预算条 0%；运行标签已在滚事件 | 等待契约生成（2–10s） |
| 4 | 任务页 → 契约与计划（`requirements-form.ts`） | 契约正文：目标 / 不做 / 验收标准 / 预算上限 / 计划步骤 N 条；底部固定操作条 `确认契约` `修改契约` `取消任务` | 点 `确认契约` |
| 5 | 任务页 → 概览（`scheduling-view.ts`） | 下一步行动卡：「契约已确认，可开始执行」；下面依次是并发档位、预算上限、员工与 worktree 预览、工作流图缩略 | 点 `开始执行` |
| 6 | 任务页 → 运行（`execution-view.ts` + `task-events.ts`） | 事件流按过程组折叠：已完成 turn 收成一行摘要，当前 `tool.started` 展开；右上实时 Token 用量（`token-usage-view.ts`） | 无需操作，可离开页面 |
| 7 | 任意页（离开后） | 页面头下方待办条出现 `等待输入 1`；任务列表该行左侧橙色等待点 | 点 `等待输入 1` |
| 8 | 交互抽屉（`runtime-interaction-form.ts`） | 问题正文、候选项 2–4 个、上下文引用（文件 + 行号）、有效期倒计时（如「剩余 9 分 12 秒」）、`提交回答` | 选一项后点 `提交回答` |
| 9 | 任务页 → 交付审阅（`delivery-view.ts`） | 交付摘要：改动文件数、增删行数、交付物列表、审阅意见框；主按钮 `通过交付`，次按钮 `打回重做` | 点 `通过交付` |
| 10 | 任务页 | 状态胶囊「已交付」，概览顶部出现「已归档到项目 · 3 分钟前」，主按钮变 `新建同类任务` | 结束 |

失败分支：第 4 步 `取消任务` 只停止后续调度，不删除 worktree；第 9 步 `打回重做` 进流程三的失败分支。

## 2.2 流程二：被交互卡住 → 回答 → 继续

前提：用户在别的页面（例如知识页编辑条目）。

| # | 屏 | 用户看到 | 下一步点 |
|---|---|---|---|
| 1 | 知识页 | 待办条新增 `等待输入 1`（1 次 300ms 轻微高亮，不弹窗、不抢焦点） | 点 `等待输入 1` |
| 2 | 交互抽屉（480px，当前页不卸载） | 抽屉头：任务标题 + 员工名 + 倒计时；正文：问题、引用上下文、候选项 | 选一个候选项 |
| 3 | 交互抽屉 | 选中项高亮（`--accent-subtle` 背景 + 左侧 3px 主色竖条），底部 `提交回答`，并提示「回答后该交互立即失效，不可修改」 | 点 `提交回答` |
| 4 | 交互抽屉 | 按钮变 `提交中…`（禁用、宽度不变，沿用现有 `aria-busy` 提交锁），成功后抽屉 156ms 收起，焦点回到打开它的按钮 | — |
| 5 | 知识页 | 待办条计数减 1；行内无提示，不打断编辑 | 继续原工作 |
| 6 | 任务页 → 运行 | 事件流中该交互合并为一行：问题摘要 → 回答摘要 → 耗时（`interaction.opened` 与 `interaction.resolved` 不再是两条） | — |
| 7 | 任务页 → 概览 | 行动卡仍是「执行中」；里程碑第 4 节点「执行」显示进行中 | 无需操作 |
| 8 | 超时分支 | 有效期耗尽：待办条计数减 1，交互卡变灰显示「已超时，任务已暂停」，主按钮 `恢复并重新提问` | 点 `恢复并重新提问` |

键位：`Esc` 关闭不提交；`Ctrl Enter` 提交；焦点进入抽屉时落在问题标题（`tabindex="-1"`），不是输入框。

## 2.3 流程三：失败 / 停止后恢复或重开

### 2.3.1 失败（`runtime.error` / 后端 `workflow-recovery` 判定）

| # | 屏 | 用户看到 | 下一步点 |
|---|---|---|---|
| 1 | 任意页 | 待办条 `失败 1`；任务列表该行状态胶囊「执行失败」（`--danger`）；运行中计数减 1 | 点 `失败 1` |
| 2 | 失败抽屉 | 错误摘要：错误码、时间、最后一条成功事件、受影响文件 ≤3 条、`查看完整日志` | 读摘要 |
| 3 | 失败抽屉 | 三个动作按风险升序、视觉主次递减：`从失败步骤重试`（主）/ `新建 Run（保留 worktree）`（次）/ `重新开任务`（危险文字按钮） | 点 `从失败步骤重试` |
| 4 | 任务页 → 运行 | 事件流插入「重试」分隔线；旧 Run 折叠成一行「第 1 次 Run · 失败 · 4 分 12 秒 · 12 条事件」，下方开始新 Run | — |
| 5 | 任务页 → 概览 | 行动卡回到「执行中」，预算进度按累计用量继续，不重置 | — |

说明：后端已有 `workflow-recovery` 的自动恢复与"已授权且已知结束的可修复失败自动恢复"策略。本设计不改该语义，只在 UI 上把"自动恢复已发生"显示为一条带时间戳的事件行，避免用户误以为任务卡死。

### 2.3.2 停止（用户主动）

| # | 屏 | 用户看到 | 下一步点 |
|---|---|---|---|
| 1 | 任务页 → 运行 | 右上 `停止运行`（危险描边按钮，不填色） | 点 `停止运行` |
| 2 | 危险确认对话框（原生 `<dialog>`，现有样式已支持 18px 圆角与 `::backdrop`） | 标题「停止当前运行？」正文列后果：① 正在执行的工具调用会被中断；② 已写入的文件保留在 worktree；③ 本次 Run 进度不能续跑，只能重试或重开。底部 `停止运行`（`--danger` 填充）/ `继续执行`（默认聚焦） | 点 `停止运行` |
| 3 | 任务页 → 运行 | 流尾出现「已由你停止 · 14:32」；状态胶囊「已停止」；用量条冻结并标注「本次 Run 已结束，不计入失败」 | — |
| 4 | 任务页 → 概览 | 行动卡三个出口：`从停止步骤重试`（主）/ `审阅已产出内容`（次）/ `重新开任务`（危险文字按钮） | 点 `从停止步骤重试` |

### 2.3.3 重新开任务（破坏性）

| # | 屏 | 用户看到 | 下一步点 |
|---|---|---|---|
| 1 | 概览 → `重新开任务` | 对话框：标题「重新开任务？」；正文「将新建一次 Run 并覆盖当前 worktree（`worktrees/t_7f3a`）。其中 7 个未提交文件会被丢弃，不可恢复。原任务契约与事件记录保留。」 | — |
| 2 | 同上 | 需输入项目名末 4 位（`t_7f3a`）做二次确认；未输入时主按钮禁用；`Esc` 关闭不执行 | 输入后点 `覆盖并重开` |
| 3 | 任务页 → 运行 | 新 Run 首条事件 `runtime.bound`；旧 Run 折叠行标「已覆盖 worktree」；用量区分「本次任务累计」与「本次 Run」两个数值 | — |

## 2.4 跨流程一致性规则

| 规则 | 值 |
|---|---|
| 破坏性操作 | 二次确认 + 后果逐条列出（≤3 条）+ 默认焦点在安全按钮 |
| 每个视图的主按钮 | ≤1 个；其余为次按钮或文字按钮 |
| 状态变化后的焦点 | 抽屉/对话框关闭 → 回到触发按钮；页面切换 → 页面 `h1`（`tabindex="-1"`） |
| 不可撤回动作 | 文案出现「不可恢复」或「不能续跑」，按钮用明确动词，不用"确定" |
| 提交锁 | 沿用现有 `aria-busy` + 按钮禁用 + 宽度不变，防重复提交（`verify-ui.mjs` 已断言只发一次请求） |
| 动效 | 抽屉 240ms 入 / 156ms 出；对话框 160ms 入（沿用现有 `apix-dialog-in`）；`prefers-reduced-motion` 下为 0 |
