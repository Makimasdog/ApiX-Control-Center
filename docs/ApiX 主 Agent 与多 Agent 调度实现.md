# ApiX 主 Agent 与多 Agent 调度实现

## 判断

此前的 Director 只是规则型目标拆分，不具备与用户持续对话、整理记忆和审查提案的主 Agent 能力。将 ApiX 定位为 Director 合理，但规划与实际执行必须分开。用户的五项反馈中，主对话、可编辑计划、运行中干预和并行角色属于核心流程；Trae、Qoder、WorkBuddy 的桌面安装发现与可托管接入则是不同能力。

## 当前流程

1. 用户选择项目，在首页进入“与 ApiX 沟通”。ApiX 通过 Pi 的无工具 RPC 读取本项目的近期主对话、可用员工和计划状态，生成中文回复与结构化协作提案。Pi 不可用时会明确标注规则型回退。
2. 用户可编辑目标、每步任务、员工和依赖，保存草案或创建待审批计划。新计划中的任务先不启动。
3. 用户检查计划后可逐步批准，也可一次批准整份预定计划。ApiX 根据依赖调度，互不依赖的步骤可并行。计划任务在 Git 项目中使用独立 worktree；最终差异仍需集成预检和明确批准。
4. 用户可在中途向 ApiX 补充要求或询问进度。主 Agent 会收到实际任务状态；单纯询问进度不会生成新计划。它可以提出新草案，但不能暗中修改正在运行的任务。未启动步骤可改任务内容和员工，原审批随之失效；也可统一取消未启动步骤。运行中任务可请求停止，再重新规划。
5. ApiX 可从主对话中提取有用户原话证据的项目记忆，保存来源消息。用户可在“项目记忆”中编辑或删除。员工 Agent 的输出不会自动成为项目事实，结构化项目档案也不会被模型静默覆盖。

## Agent 发现与并行边界

- Pi 和 Codex CLI 是已验证的托管 Runtime，可注册多个逻辑员工。两个 Codex 员工在不同对话中可运行两个进程；普通任务共享项目目录，可能发生文件冲突。需要隔离的编码任务走 Director 协作计划。
- Windows 开始菜单扫描可发现 Trae、Qoder 和 WorkBuddy 的安装条目。发现不等于可控制；没有验证适配器时只能显示“仅发现”，不能注册为托管员工。后续接入应逐项验证启动、会话、事件、停止与权限边界。
- 主 Agent 使用 Pi 当前配置的认证与模型。它本身禁用工具，不直接执行文件操作；员工启动、工作目录和执行内容仍由后端审批约束。
