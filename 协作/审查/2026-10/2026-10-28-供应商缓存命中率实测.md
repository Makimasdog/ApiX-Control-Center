# 供应商缓存命中率实测（Codex 自审）

本轮实测结论：ApiX 当前配置模型 qwen3.8-flash，节省模式下连续完成两次相同只读任务，共 8 次真实 API 请求，**有缓存命中的请求为 7/8（87.5%）**，**输入 Token 的加权缓存占比为 33,792 / 72,600（46.55%）**。这两项描述不同，不能把“所有请求都有部分命中”解释成“全部输入都被缓存”。

## 条件与来源

- 版本 e5483e8；香港时间 2026-10-28 11:00:49–11:04:28。
- 模型配置 apix-custom / qwen3.8-flash / openai-completions，两个全新对话均启用 saving，模型前后配置一致。没有更换供应商、修改业务代码或主动清空供应商缓存。
- 与前次对照使用逐字相同的只读任务：读取 package.json、context-optimizer.ts、model-usage.ts 并核查原 7 项问题。提示词 SHA256 为 `1485ef77601ba9e49792c90ade5ddfabe8272b95d580b9dfb96d77b31068fc38`，实际读取的来源文件哈希与前次记录一致。
- 每次均为 3 次 read_file + 最终回答，无 read_context；两次任务 completed、交付 netChanges=[]，基线/最终 manifest 均为 `2c42cb80ae05ed13478391efdf771545599b446faee0c8a30ac44a63a16d3651`。没有修改项目文件、执行命令或委派。
- 读取真实任务账本 cachedInputTokens，即 Chat Completions API 返回的 `usage.prompt_tokens_details.cached_tokens`，不是请求正文估算值或本地答案缓存。两次账本的 input/cache 与逐次求和一致。

## 两种统计口径

1. 请求命中比例：已观测到缓存计数的请求中，cachedInputTokens > 0 的比例。
2. 输入 Token 缓存占比：有输入及缓存观测的请求，SUM(cachedInputTokens) / SUM(inputTokens)，采用 Token 数加权，不平均每次的百分比。

本轮 8/8 请求的输入与缓存计数完整，因此分母覆盖全部请求。未知计数不能当作 0；若缺失计数，只能报告已观测子集并说明覆盖率。缓存属于输入子项，不再加入输入总量，输出 Token 不进入这个命中率分母。

首个请求本次返回 0，第二次任务的首请求返回 3,072。该现象表明这些请求中有供应商报告的缓存读取；没有记录最终完整发包前缀诊断，不能据此确定究竟哪些前缀字段被缓存、TTL 或路由规则。两次输出分别 4,586 / 4,797 Token，输出长度和思考存在差异，耗时不能单独归因为缓存。
