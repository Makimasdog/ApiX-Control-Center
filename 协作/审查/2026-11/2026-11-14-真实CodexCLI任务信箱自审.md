# 真实 Codex CLI 任务信箱自审

2026-11-14 · Codex 本地自审 · `codex/external-agent-workbench`

用已登录 ChatGPT 的 `codex-cli 0.167.0-alpha.4.1`，通过 ApiX 的普通 CLI 后端而非 App Server，在独立服务和临时 Git 项目中验收。实际 Codex 负责发问、请求本机信箱、确认答复、执行写入和集成运行；ApiX 管理者的规划、证据选择、质量评语由本地测试替身提供。信箱、权限、运行和验收状态、文件、Node 检查及冻结全部走生产实现。员工收到的任务只描述要问什么和做什么，由它根据通用启动说明自行调用信箱。

首次实测已经有一条员工信箱提问、README 依据和接收回执，但该次运行在验收前停止，不能算交付通过。第二次明确保留更长的有界测试窗口，发现 Windows 上员工第一次确认请求没有按服务要求发送 JSON；员工随后重试成功，而且正确识别出测试任务的目标文本与冻结架构常量不一致，未擅自写入。修订启动说明，明确完成回执需要 JSON 请求头和空对象；对齐测试规划与验收契约。不变更生产时限、原有审批或 CLI 回执校验。

下一次运行已完成真实员工代答、写入和模块验收，最终集成时 Git 将文件检出为 CRLF，和该场景的字节级 LF 要求不同。集成员工也通过信箱发问。测试仓库随后明确加入 `.gitattributes` 的 `a.txt text eol=lf`，把文件约定随交付一起传递，避免依赖开发机的全局 Git 设置。

所有真实员工试跑都主动用了信箱，没有出现只在终端打印问题的行为；但另有两次长时间没有员工公开输出，最终按运行时限停止。终端问句接管在独立夹具中已覆盖“只打印问句后以零码退出”的路径，并完成自动验收。本次结论限这个版本、登录方式和隔离场景，不证明其他 CLI 或供应商同样会遵循说明。

最终组合回归 4 项通过，覆盖原生结构化问答、普通 CLI 信箱问答、终端问句接管和已授权派工复用；构建、静态检查和 diff 空白检查通过。终端接管端到端使用生产服务和真实 Node 验收，模型输出协议使用确定性替身；本轮没有用真实模型强制复现该问句格式。
