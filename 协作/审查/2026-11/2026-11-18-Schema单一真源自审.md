# Schema 单一真源自审

更新：2026-11-18。分支 `feature/structural-hardening`。本轮未推送、未合并。

## 起点：问题是什么

审计时发现 schema 分两套，谁都不管谁：

| 来源 | 表数 | 版本管理 | 执行时机 |
|---|---|---|---|
| `control-plane.mjs` 迁移块（v1–14） | 39 | 有 `schema_migrations` | 按 `if (!version)` 逐条 |
| `src/**` 各模块工厂 | 69 | **无** | 每次启动无条件执行 |

具体后果：

1. **加一列要改多处**：建表语句、`PRAGMA table_info` + `ALTER`、测试里手抄的副本。
2. **新装库与升级库可能不同**：`CREATE TABLE IF NOT EXISTS` 在表已存在时完全不看新定义，往建表语句里加列而不写迁移，新库有这列、老库没有，**且不会报错**。
3. **没有全局视图**：review 时无法判断一次 schema 改动的影响面。

## 做了什么

### 第一步：让 schema 可审查（`5a49beb`）

新增 `scripts/schema-snapshot.mjs`：

- `--boot`：用隔离数据目录真实启动一次控制平面，导出规范化 schema
- `--dump <db>`：导出指定库
- `diffSchema()`：逐表/列/类型/非空/默认/索引比对

两个守卫：

**`test/schema-baseline.test.mjs`** — 新装建出的库必须与 `test/fixtures/schema.snapshot.json` 一致。任何结构变更都会失败，迫使改动人同时更新基线，基线 diff 就是 review 材料。

**`test/schema-upgrade.test.mjs`** — 老库升级后的结构必须与新装完全一致。起点用**冻结**的 `test/fixtures/schema-v1.sql`。

这里有个关键取舍：起点**不能**从 `control-plane.mjs` 现取。迁移 1 用的是 `CREATE TABLE IF NOT EXISTS`，在老库上整段跳过、只影响新装；若从当前源码现取，"往迁移 1 加列但忘了写迁移"会让两条路径一起漂移，测试全绿——守卫变成摆设。我实际验证过这一点：用现取版本时注入漂移测试仍然通过，换成冻结副本后立刻失败。

### 第二步：DDL 集中（`785c1a3`）

新增 `src/infrastructure/schema.ts`，35 个模块的全部 `CREATE TABLE` / `CREATE INDEX` 文本集中于此。

- 29 个文件、37 处 `db.exec(\`...CREATE TABLE...\`)` 替换为 `ensureModuleSchema(db, key)`
- `ensureModuleSchema` 用内容 SHA-256 记录在 `module_schema_versions`：哈希未变则跳过（启动零 DDL），变化后重跑一次
- `control-plane.mjs` 在迁移块之后调用 `applyAllModuleSchemas(db)`，让新装与升级走同一套模块建表逻辑

保留在模块内的唯一例外：`knowledge-base.ts` 的 `kb_fts`。它是 FTS5 虚拟表，建表语句取决于当前 SQLite 是否编译了 FTS5（不可用降级为普通表），属于运行时能力探测而非静态结构。

### 第三步：消除双声明 + 加守卫（`39045cf`）

集中时暴露出真实漂移点：`assistant_notes` 同时由 `assistant-loop.ts` 和 `project-memory.ts` 各自声明。两处定义当前恰好一致，但 `IF NOT EXISTS` 会静默忽略后者的差异——谁先执行决定最终列集。按语义归 `project-memory` 所有，从 `assistant-loop` 块移除。

新增 `test/schema-source.test.mjs`（3 项）：

1. 模块源码不得内联 `CREATE TABLE`（`kb_fts` 与 `control-plane.mjs` 迁移块按设计例外）
2. 注册表键唯一、同一张表不得多处声明
3. `ensureModuleSchema` 对未知键报错、相同内容不重复执行

## 验证

- **全库结构不变**：112 张表 → 113 张（仅新增注册表 `module_schema_versions`），表名、索引数（33）完全一致，无缺失无多余。
- `npm run check` 通过（tsc + node --check + stale-dist + eslint --quiet）。
- 模块级回归 202 项：201 通过、1 跳过、0 失败（workflow/coordinator/scheduling/messaging/agent-health/workflow-recovery/memory/project-memory/token-usage/architecture/autonomy + 全部 schema 与终态测试）。
- schema 四套守卫 + project-memory + assistant-loop 共 105 项通过。
- **守卫有效性实测**：往迁移 1 注入一列但不写迁移，`schema-upgrade` 立即失败并报「升级路径与全新安装不一致（1 处）」。

## 没做

- **迁移块本身没有重构**：`control-plane.mjs` 的 39 张表仍是"逐条 if + 裸 BEGIN"的写法，没有换成 `PRAGMA user_version` 驱动、没有拆成 `migrations/0001_*.sql` 文件序列。这部分有版本管理、行为正确，改造收益低于风险，留作后续。
- **测试里手抄的 DDL 没删**：32 个测试文件各自建最小表集。它们不是生产 schema 的副本，而是各测试需要的最小子集，强行统一会让测试耦合到全库结构。现在的保证是"生产源码只有一份 DDL"（由 `schema-source` 守卫）+"新装=升级"（由 `schema-upgrade` 守卫）。
- **没有做数据迁移验证**：只验证结构等价，没有验证"老库有数据时升级"的行为。当前所有迁移都是加表/加列/加索引，不改既有数据，风险较低；若将来有改数据的迁移，需要单独的场景测试。

## 边界

- 未运行 `test:ui:*` 与真实模型批次。
- 这是自审，不是独立审查或人工验收。
