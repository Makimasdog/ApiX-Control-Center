# 多 Agent 协作加固（P0：运行终态与停止语义）自审

更新：2026-11-18。分支 `feature/agent-collaboration-hardening`（基于 `codex/external-agent-workbench` 的本地 HEAD `e97627a`）。本轮未提交、未推送、未合并。

## 范围

本轮只做多 Agent 协作流程的第一阶段：让 Run 的终态可信。新增的编排/路由/契约改造不在本轮，见文末「未做」。

## 问题

1. `control-plane.mjs` 的 `setRun` 无条件 `UPDATE runs`。健康检查把 Run 判为 `unknown` 后，`running` Map 仍在，迟到的 `finishRuntime` 还能把同一 Run 改成 `completed`，并再次结算预算、再次推进 DAG。
2. `stopping` 期间原生 `turn/completed` 仍会按成功收尾，停止请求等于被迟到回合覆盖。
3. `setRun` 没有「只写一次」的边界，重复收尾会重复写 Task 状态、消息事件和后续调度。
4. 三个监督器（健康检查、原生交互、主动监督）共用一个 try/catch，任一探测抛错会连带跳过其余两个。
5. `reviseSession` 先让计划失效再请求停止，员工问答会在计划失效后失败并等到超时。

## 改动

### `src/coordination/run-finalizer.mjs`（新增）

唯一的 Run 终态入口：

- 只有 `starting/running/stopping` 能进入终态，且只写一次（条件 UPDATE 做 CAS）。
- 已是终态（含 `unknown`）时返回 `changed:false`，不重复结算、不重复推进。
- `stopping` 状态下拒绝 `completed`，返回 `rejected:'STOPPING_CANNOT_COMPLETE'`，由调用方按停止证据收敛为 `cancelled` 或 `unknown`。
- Run 终态、Task 状态、预算结算在同一个 SAVEPOINT 内提交；`settle` 抛错整体回滚，状态与账本保持一致。
- DAG 推进放在提交之后，通过 `afterCommit` 回调执行；`deferAfterCommit` 允许调用方在产物落库后再推进。
- `unknown` 不结算预算、不推进 DAG。

### `control-plane.mjs`

- Schema 迁移 13：`runs` 新增 `finalized_at`、`stop_evidence`。
- `setRun` 保留为兼容包装：非终态直接更新，终态转交 `finalizeRun`。
- `finishRuntime` 重排为「CAS 认领终态 → 写产物与消息 → 推进依赖」，避免下游读到空交付。
- 收尾被拒时只做清理，迟到输出记为 `late_output` 事件，不改写任务结果或验收状态。
- 已请求停止但没有停止证据的 Run 收敛为 `unknown`，不再记为成功。
- 监督 tick 拆成三个独立 try/catch，单个失败不影响其余监督。
- 新增 `parallelScope`：同计划并行任务**双方都声明了写入范围且重叠**时阻塞派发；未声明范围不改写既有并行语义，只记录一次 `task.parallel_scope_unverified` 供审计。

### `src/coordination/coordinator.ts`

`reviseSession` 先请求停止旧 Run，再让需求版本失效并回到 `clarifying`。
