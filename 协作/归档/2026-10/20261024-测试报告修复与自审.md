## 修复范围与根因

- **npm 11 logic 失败**：Node 24.22.1 + npm 10.9.2 原夹具通过，切换 npm 11.19.0 后真实复现失败。保留隔离副本，读取 SQLite 命令日志和 npm debug log，明确报错为 `TAR_ABORT / max decompression ratio exceeded: 1000.19 > 1000`。9 MiB 重复字符夹具被压到约 10 KiB，触发新版 npm 的归档解压比限制。大文件夹具改用 gzip level 0，保留真实大依赖扫描；不放宽生产解压限制、不扩大 minimal-v1 环境白名单、不继承宿主凭据。相同 npm 11 logic 用例修正后通过。
- **HTTP 413 后 ECONNRESET**：统一请求体读取器，超限后释放已缓存内容并读完剩余请求再抛结构化 413；其他经 JSON 错误出口且尚未读完请求体的早拒绝响应声明 Connection: close。保留旧接口 30000 字符/登录 1000 字符与项目工具接口按字节计数的原契约，UTF-8 跨块由 StringDecoder 处理。回归检查同一个 http.Agent 的同一个 socket：上传/工具/旧接口/登录超限后紧接 GET 均成功；另核对中文字符与字节上限差异。
- **错误语义**：events/stream、chat-history、mailboxes 缺 projectId 返回明确 400。SQLite 与运行时 TypeError/ReferenceError 返回 500/INTERNAL_ERROR，详细原因记本机 stderr，客户端不回显内部表结构；既有 ToolError 状态和旧业务错误 400 保持兼容。这不是对所有遗留错误的一次性重分类。
- **Windows 稳定性**：command-bridge 与 command-lifecycle 的就绪等待改为 25ms 文件存在轮询，避免相关测试触发 fs.watch 原生断言；清理增加有限重试。非 Git 基线发布对 EPERM/EACCES/EBUSY 最多重试 5 次、总等待 750ms；其他错误立即失败，失败后清理私有 staging，不发布半成品。注入 EPERM/EIO 验证成功重试、次数上限、源文件保留和失败清理。
- **支持矩阵与测试接线**：engines、npm runtime 检查、桌面开发/构建守卫及文档统一为 Node 22.19–22.x / 24.22+（24.x），npm 10/11。CI 两组固定 npm 版本为 10.9.2 / 11.19.0，覆盖 Node 22.19.0 / 最新 24.x，并运行桌面模块测试。model-endpoint/project-scan 纳入 npm test，诊断工件按 Node 版本分名。
- **依赖**：只更新锁文件的 body-parser 2.3.0 → 2.4.0、fast-uri 3.1.8 → 3.1.9；官方 registry 的 audit fix/audit 返回 0 vulnerabilities。本机 Electron/electron-builder 和 Electron 二进制已存在，npm ls 无缺失；补充完整 npm ci 与 omit=dev 的区别，无需重复添加已声明依赖。
- **界面**：无目录模型时显示可理解占位提示；连接测试区域默认展开；原生表单 invalid 事件同步到 aria-live 状态区。浏览器验证新增空表单与连接按钮可见性检查，桌面/390px 布局截图已查看。供应商失败路径改为真实后端版本冲突，代替在本机 Playwright 环境导致后续请求悬挂的合成 fulfill 响应；仍检查保存成功/绑定未变/凭据清空与后续恢复。
- **可维护性**：主要 Git 夹具显式禁用 autocrlf，私有基线仓库固定该配置，不改变用户全局 Git 配置；stdio 演示移动至 test/manual/mcp_demo.py，并更新启动说明。
