# Agent 消息幂等开发与自审

日期：2026-10-24
分支：`Kimi/agent-reliability`
审查性质：开发者自审，不是独立审查或人工批准。

## 范围与目标

本轮只完善主 Assistant 的消息接收可靠性：为可选请求 ID 提供 `(session_id, request_id)` 范围的持久幂等，避免网络重试或重复提交创建重复用户轮次及重复下游推理。未改变既有副作用凭据的恢复语义，也不宣称外部副作用 exactly-once。

## 实现审查

- `src/assistant/assistant-loop.ts`：新增持久消息回执；内容使用 SHA-256 绑定。相同会话、相同 ID、相同内容直接返回当前会话，不再次触发 `kick`；同 ID 不同内容返回 HTTP 409 `MESSAGE_REQUEST_CONFLICT`；无请求 ID 的旧客户端保持可用。
- 首次接收使用 `SAVEPOINT assistant_message`，将交付初始化、用户事件、请求回执和会话运行状态放在同一原子范围；回执写入失败会回滚用户事件与运行状态，不启动推理。
- 重复回执在安全状态、等待选择及恢复门禁之前返回，确保已经受理的请求在运行中、完成后及重启后都可安全重试；不同内容冲突不会被误当作成功。
- `web/assistant.ts`：响应不确定时保留同内容请求 ID；正式响应或后台刷新观察到对应用户事件后清除待重试状态。后台刷新确认还会清除该次发送错误及未修改的输入草稿，避免错误状态与已确认事件并存导致再次重复发送。
- `README.md`：只更新主对话持久去重能力说明。
- 访问边界未扩大：沿用现有 owner HTTP 边界、项目/会话查询和权限检查；请求 ID 不进入命令执行或模型授权。事件中的请求 ID 仅用于客户端确认与去重。

## 自审发现与修正

真实浏览器首轮验证发现：响应丢失后，后台刷新已经观察到正式事件，但旧逻辑只清除请求 ID，仍保留发送错误和输入内容，紧接着重试可能生成新 ID 并产生重复轮次。已修正为正式事件确认时同步完成该次不确定发送的界面恢复，并用重建后的真实页面重新验证。

最终差异复核覆盖新增表、事务回滚、重启去重、冲突错误、调用方及浏览器确认竞态；未发现新的访问边界或数据一致性问题。

- `npm run check`：通过。

- Node 24.22.0，`assistant-loop.test.mjs`：57/57 通过，包括运行中去重、重启后去重、冲突、非法 ID、跨会话隔离和 SQLite 回执失败回滚。
- Node 24.22.0，真实 HTTP 消息幂等用例：通过；重复提交版本不变、仅一个用户事件、不同内容返回 409。
- Node 24.22.0，完整测试：483/485 通过。`model-lifecycle` 的 149/150 ms 文本断言失败在单独复测中通过；`assistant-verification` 的 Windows 临时目录清理 `EPERM` 在单独复测中仍可复现，属于本轮未修改的既有清理问题，未宣称完整套件全绿。
- 最终组合复测另有一次既有协作用例的 9 秒服务启动等待超时；该用例与真实 HTTP 幂等用例随后单独复测均通过（2/2）。
- 真实浏览器隔离数据目录验证通过：
  1. 首个请求已受理但响应被测试装置丢弃，后台刷新观察到正式事件后清除错误和草稿，服务端仅一个用户事件。
  2. 阻止正式状态刷新的情况下，同内容立即重试复用同一请求 ID，两次 HTTP 200 但服务端仅一个用户事件。
  3. 正式确认后再次主动发送相同内容使用新请求 ID，服务端形成第二个用户事件。
- 浏览器验证未配置付费模型；覆盖消息接收、去重和界面恢复，不声称完成付费模型端到端推理验收。
