## B：源码、环境和产物绑定

`VerificationContract` 增加可选 `npm` schema 1，不新增表。候选由宿主从项目生成，包含确切安装参数、各检查 npm 参数、脚本实际内容和固定顺序、运行时身份、网络选项、安装与环境策略、固定产物目录及 protectedFingerprint。保存的契约体本身也必须匹配版本哈希，不能仅保留 version 后改写运行时或参数。模型只有申请接口，始终请求用户批准；UI 批准要求会话版本、契约版本和项目准入门槛。

源码预算 3000 项 / 8 MiB；依赖 40000 项 / 256 MiB；单产物目录 6000 项 / 32 MiB。源码包含其余普通输入，已知凭据文件（含根与嵌套 .npmrc、.env、私钥扩展）、Git、用户 node_modules 不复制；自动快照、文件入口与代码搜索采用相同 npm 凭据排除规则。npm 模式并未沿用通用 `.tmp*` 忽略。复制逐块限量，副本和源再次校验哈希。每次检查都使用新副本，依次执行全部必要检查，不能用旧 build 跳过新构建。

`dist`、`coverage` 是宿主固定候选；可修改范围不得覆盖 package/lock、vendor、tests/scripts 或产物。源目录已有非空产物时拒绝批准并要求核对。脚本/lock/config/范围/运行时/下载策略变化导致旧契约失效；源码正常修复不需要重批冻结检查，但必须重新运行检查。确需修改冻结文件时显式生成并批准新契约。

## C：真实 npm 准备与执行

`src/npm-validation.ts` 在现有数据目录拥有的 `npm-validation/run-*` 创建源码副本，调用原 `assistantCommands.execute` 的宿主 context（不注册给模型）。依赖在副本中通过真实 `npm ci` 安装，不 mock 安装成功、不引用或共享源 node_modules，不使用跨任务缓存。

默认安装脚本关闭、无下载批准时 `--offline`；有批准也仅支持 npm 公共 registry。用户/全局 npm 配置使用两个独立空文件；环境仅保留必要 Windows 变量与固定 PATH、私有 TEMP/HOME/cache、CI。不会继承任意 NODE_OPTIONS、npm 配置、模型凭据或 `.env`。npm 安装生命周期、项目检查脚本和付费模型批准分开处理。

npm 10 `ignore-scripts` 不执行安装脚本；显式 npm run 仍执行目标脚本，并省略自动 pre/post。因此宿主按批准顺序分别执行 pre/main/post，所有命令均有 operationId、终态与日志。实际安装后的依赖全树清单/哈希/容量与版本、lock、配置策略一起保存；每个脚本后核对源码及依赖，不能只用 lock 哈希声称不可变。

成功、失败、取消、准备不完整、未知分别记录。源工作区在执行期间变化会拒绝当前验收；不会回写或覆盖用户修改。所有安装与检查命令的日志引用在正式验收时重新核对，缺失/过期不能靠最后一条成功命令绕过。失败副本和日志保留；重启不重放。存储最多 20 次，启动前已有资料超 1 GiB 则拒绝，单次容量监测另限 60000 项 / 384 MiB，每 1.5 秒检查并取消超限运行；是有界监测，不是硬磁盘配额。
