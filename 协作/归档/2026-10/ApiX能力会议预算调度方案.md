## 一、员工能力档案与任务画像

员工档案记录：员工 ID、CLI/适配器、声明模型与实际观测模型、能力标签、语言/框架、工具、项目熟悉度、上下文限制、实时消息/规划会议支持、账务账户别名、更新时间及版本。禁止保存密钥；账户别名仅用于区分或关联用户明确配置的同一账户。

能力证据分三类，页面和调度均保留来源：用户声明、员工自述、已验收任务记录。未经验证的自述不提高硬能力等级；供应商宣传或品牌名称也不作为成功证据。历史观察按员工+模型+任务类型统计，模型变化后不沿用旧模型分数；无样本显示未知，冷启动用用户声明作为待验证参考。

任务画像记录：目标、语言/技术栈、任务类型、交付物、验收标准、风险、必要工具、读写范围、依赖、预计上下文、截止时间和用户指定员工。任务类型优先沿用实现/测试/审查/分析/文档，不添加一套庞大行业分类。

验收率与耗时只是同类任务证据，必须展示样本量；取消、额度中断、环境故障不直接当作能力失败，不能通过“任务进程退出 0”认定质量成功。

## 二、均衡调度与解释

先过滤硬条件，再对可行员工比较，不让综合分数抵消权限、工具或预算不满足。

1. 硬过滤：员工启用/运行时可用、实际任务所需工具、项目访问规则、权限、用户指定约束、暂停状态、有效额度与预算策略。
2. 质量门槛：必要能力和验收要求成立；高风险任务要求可用的独立审查者，没有则明确自审/人工审查，不假造独立审查。
3. 可行候选比较：能力证据、同类已验收记录、预计返工、费用区间、预计完成时间、已有任务排队和上下文交接成本。用户不需要填写一组难解释的权重。
4. 均衡模式先达到质量门槛，再剔除费用/时间均明显更差的候选；以透明的项目策略选择剩余候选。估算无法区分时保留并列、展示未知和证据，用户可改派。
5. 生成可审查理由：选谁、为什么、候选为何未选、费用/时间区间、数据来源和更新时间。模型可解释和提议，最终权限与准入由后端规则决定。

预算低不意味着一定派低能力员工。应优先缩小任务范围、减少无效上下文、跳过不必要会议、保留关键审查，再明确告诉用户哪些约束无法同时满足。

## 三、规划会议：讨论认领而非自动夺权

建议流程：确认需求 → ApiX 草案与候选 → 会议预算预检/批准 → 员工独立提案 → 可选交叉讨论 → ApiX 汇总新版计划 → 用户审查批准 → 执行 → 验收与反馈。

- 首版支持用户手动开会；均衡模式不强迫每个小任务开会。跨模块依赖、责任重叠、候选分工不清或高风险时推荐开会。只有一个可用员工时显示单人规划，不能称多 Agent 会议。
- 第一轮各员工独立思考，输出结构化认领：愿意完成的步骤、理由与证据、必要输入/工具、能力边界、文件范围、交付物、风险、耗时和用量估算。允许拒绝认领，避免全员都声称无所不能。
- 第二轮只在责任冲突、遗漏或技术方案矛盾时进行，向员工发送其他人的必要提案摘要，要求回应具体异议；无需传递完整历史或私有推理。记录可见提案、理由和纪要，不要求暴露隐藏思维链。
- 初始限额：至多 3 位相关候选、最多 2 轮；时长与生成限制按适配器已验证能力执行。超时、断连、额度失败或预算预检失败均保留真实记录，ApiX 汇总可用提案或交给用户，不虚构共识。
- 主持者负责发现无人认领、重复认领、审查者与实现者重合、文件重叠、依赖成环及预算缺口。Agent 的自荐只是建议，不能修改已确认需求、赋予权限、扩展工具或启动生产任务。
- 会议与执行使用不同的活动 ID/运行身份和消息路由，会议消息不能被执行任务误领。会议批准仅涵盖讨论；形成新版计划后需要当前版本的执行批准。
- 增加经过验证的 consultation 能力入口。不能把“只读讨论”提示当作系统级禁写；没有适配器工具约束证据时，不将普通员工 CLI 标为安全无工具讨论，也不沿用 full_access 来开会。
- 纪要包括各员工提案、分歧、接受/拒绝原因和未解决风险。会议失败不会绕过审批，也不会把成果评审 meeting_review 自动改成分工会议。

## 四、额度与费用：两种账本

额度账本：订阅窗口、已用/剩余比例、重置时间、账户别名、来源、观测时间、可信度。费用账本：API/按量账单、币种、实际模型、单价版本、输入/输出/缓存 Token、额外工具费用、估算区间、已预留和已观测用量。

关键规则：

- 优先使用有授权且正式支持的额度来源；首版允许用户手动填写，并记录时间与来源。无法查询时显示未知，不抓取 Cookie/私有端点，不把未知视为无限或 0。刷新失败保留旧值并标过期。
- 同一账户可被多个员工/项目共用，预留以账户为单位，防止多个并行任务重复使用同一余额。预留使用数据库事务和版本，会议也预留；进程结束、取消、启动失败后按状态释放/结算，不重复计算。ApiX 无法完全掌握其他终端/设备的消费，启动前重新核对可得信息。
- 订阅百分比不能直接转换为美元或固定任务次数；不同模型、上下文和任务复杂度影响消耗。无可靠转换关系时提供预算风险提示，不能伪造金额。
- API 估算采用用户/官方来源的具体模型价表，货币按最小单位存储，不隐式换汇。输入、输出、缓存读写分类按供应商语义计算，不能把 cachedTokens 同时重复算为普通输入，也不能把缺失字段当作测得 0。
- 成本预计包括 ApiX 主持/规划、会议、执行、审查和有限重试。根据同类任务报告给出区间与样本量；无样本时采用用户填写的用量上限并标低置信度，不编造精确的 $0.xx。
- 用户可设置项目总预算、单任务预算、会议预算、重试上限和额度保留量。严格预算模式下金额/额度未知需用户明确批准相应限额，不能自动购买 credits、换账务账户或开启额外付费。
- 派发前重新计算“已观测 + 已预留 + 当前预计”，超出配置上限不启动。运行中报告超预算后停止新派发、请求可支持的停止，并展示风险。启动准入或停止请求不能保证第三方正在处理的请求不会再产生费用，不宣称供应商级硬账单封顶。
- 重新规划/换员工时释放旧预留、生成新预留与审批版本；运行中的旧任务不直接换身份。保留部分成果及原有 Git 指纹/消息隔离。

官方边界核对于 2026-10-12，不固化价格数字：

- [OpenAI Docs：Pricing](https://learn.chatgpt.com/docs/pricing)：任务大小、模型和上下文影响用量，订阅额度与 API-key 计费分开，当前额度以 usage dashboard/CLI 状态为准。
- [Claude Code：Manage costs effectively](https://code.claude.com/docs/en/costs)：会话 Token 成本为估算，订阅用量和 API 账单需分别理解；权威账单来源不是 ApiX 自行估算。

这些公开文档不证明 ApiX 已能读到用户账户的额度；正式适配器需另外验证。

## 五、扩展到执行中的可靠协作

| 扩展 | 目的与边界 |
| --- | --- |
| 文件/模块责任范围 | 防止分工重叠；Git worktree 仍独立，租约锁不能保证外部程序不改文件 |
| 上下文交接成本 | 有历史上下文的员工可优先，必须比较节省与偏差风险，换员工交接必要资料与冻结代码 |
| 关键路径与资源 | 优先解除阻塞后续任务的工作；不为并行而启动无输入任务，不让廉价任务长期饿死 |
| 双方交叉审查 | 实现者不负责证明自己“独立审查通过”；证据可追溯到具体员工/模型/Run |
| 受限重试与升级 | 普通故障与能力不匹配分开，先保留成果，再建议换模型/换员工；预算内有限重试 |
| 结果反馈 | 基于用户验收、返工和实际用量校准同类任务；无样本、环境故障及模型变更保持不确定性 |

## 六、分阶段实施与双 Agent 分工

旧 C7/L7 排队改派保持为执行恢复子任务；新需求优先推进 S1，S2/S3 等接口与预算基础通过后实现，不把三层同时塞入一个大提交。

| 阶段 | Codex 后端 | Claude 前端 | 验收标准 | 状态 |
| --- | --- | --- | --- | --- |
| S1 能力与资源基础 | 版本化员工档案/账户预算；确定性的过滤和候选解释；接入计划输入，拒绝无来源额度/伪造价格 | 员工能力、账务类型/额度快照配置；候选与未知/过期状态展示 | 岗位不覆盖硬能力；未知不是无限；共享账户不重复预留；过期配置不能覆盖 | PLANNED |
| S2 规划会议 | 独立会议身份、批准/预算、提案/异议/纪要、新计划版本、超时和失败处理 | 开会前成本提示、员工认领、分歧与纪要、批准新版计划 | 会议不得执行代码；缺席/失败不伪造共识；未批准不进入生产任务 | WAITING S1 |
| S3 执行与反馈 | 启动前资源重检、C7 排队改派、预留结算、估算和实际校准 | L7 改派、等待原因、预估/已报告用量、低额度与返工记录 | 并发不超额；重试/取消不重算；旧批准/指纹失效；未知费用保持未知 | WAITING S1/S2 |

文件归属延续第三轮：Codex 管理 `src/`、`control-plane.mjs`、`server.mjs`、后端测试、`package.json` 和共享文档；允许必要时新增 `src/scheduling.ts`、`src/scheduling-store.ts`、`test/scheduling.test.mjs`。Claude 管理 `web/coordinator.ts`、`web/employee.ts`、必要的 `web/execution-view.ts`/新前端模块、相关 CSS 和实际前端模块测试。不新增依赖，不覆盖用户原有文件，不并行编译 dist；跨归属修改先交接。

S1 接口先由 Codex 提供明确 schema/版本/错误语义，再由 Claude 接入。候选询价不能执行任务或消费真实模型额度。S2 调用真实员工才可能消费额度，必须有用户批准及测试适配器。未经实际接入，页面不能展示“实时账户余额”。

Codex/Claude 先各自自审，再互审对方最终 diff；审查后代码变化重新验。集中执行适当模块/HTTP 回归与隔离浏览器；真实 CLI、正式额度查询和实际账单最后单独验收。明确清单暂存，核对被审查 Git blob 后本地提交，不推送。
