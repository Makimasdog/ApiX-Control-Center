# 对话验收与验收面板修复自审

日期：2026-10-16。分支：`codex/readiness-p0-p2`，基线 `65354f1`。本轮由 Codex 实现并自审，未启动其他 Agent；不是独立审查或人工批准。

## 问题与根因

用户在另一台电脑的 `127.0.0.1:4173` 反馈：发送“确认验收”后 ApiX 声称验收通过，任务实际仍未验收；“查看变更并验收”按钮没有可见反应。本机该端口未运行，因此没有直接读取、修改或验收那台电脑的 KMeans 项目。

代码中确认两条断链：

1. 目标工作台 `coordinator.discuss()` 仅把消息交给模型并记录自然语言回复，未把明确验收请求接入宿主 `acceptTask()`。
2. `renderDelivery()` 将验收面板插入默认关闭的 `desktop-inspector`，没有展开、滚动或焦点提示。

## 实现范围与使用契约

- 新增 `src/task-review.ts`：只识别明确验收命令，如“确认验收”“确认验收任务 1”“通过任务 1 验收”。问题、引用、否定和额外指令不构成验收授权。
- `coordinator.discuss()` 在模型推理前处理明确请求。只使用当前会话计划中的真实任务；多个 completed 任务必须明确指定编号，不能猜测。
- 没有已查看版本的指纹时，宿主明确回复“尚未验收”并返回 `reviewTaskId`，客户端读取实际交付并打开面板。核对后可以点击“通过验收”，或再次发送明确验收命令。
- 已查看指纹通过 `reviewedDeliveries` 随对话请求提交；宿主调用原 `acceptTask()`，由原 `codeHandoffs.freeze()` 复核当前代码指纹、冻结 Git 交付，再写入 accepted 并推进依赖。不会绕过原验收接口的代码一致性检查。
- 已绑定且未完成的自动质量契约拒绝聊天人工放行，避免跳过自动测试与审查。
- 前端统一 `inspectDelivery()`，同时服务按钮与对话返回的面板请求。成功打开后展开工作详情、滚动到面板并聚焦；任务状态变化时移除旧面板，防止继续操作旧状态。
- 补充模型身份约束：讨论本身不修改验收状态，必须以宿主真实任务字段和执行结果为准。关键命令路径不依赖模型是否遵守该提示。

## 最终差异自审

范围：`src/task-review.ts`、`src/coordinator.ts`、`src/apix-agent.ts`、`control-plane.mjs`、`web/coordinator.ts`、两份相关测试、本记录和浏览器截图。

1. 已追踪全部调用方：`createCoordinator()` 仅在控制平面装配，新增 `reviewTask` 注入复用原验收函数；JSON 与 SSE 消息路径共用 `discuss()`。旧按钮仍使用 `/api/tasks/:id/review`，没有更换后端验收语义。
2. 只由用户最新、完整、明确消息触发写入；模型输出、历史消息、引用或错误文本不能触发该路径。任务从当前计划内选择，不能提交其他会话的 taskId 进行验收。
3. 不自动取得最新指纹来替用户认可未查看的代码。无指纹、过期指纹、已变化代码、非 completed 状态、模糊多任务和未完成自主契约均不产生假验收。已有 accepted 任务再次确认只返回实际状态。
4. `acceptTask()` 原先的冻结、状态、事件与依赖推进逻辑保持不变。明确验收命令不请求模型，不新增模型费用或授权额度；下游仍受原任务授权、并发、预算和工作区准入约束。
5. UI 跨项目/会话检查保留，异步检查结果不会插入其他会话。真实任务变化后移除旧面板；指纹仍由验收时再次核对，页面展示或缓存不替代服务端校验。
6. 新响应只增加可选 `reviewTaskId`，未修改数据库结构和既有历史状态；没有补写用户远端项目的历史“验收通过”记录。
7. 没有新增依赖、自动切分支、推送或合并。用户已有 `.gitignore`、Skills 和其他未跟踪文件保留；最终暂存使用明确文件清单并逐一核对 Git blob。

结论：本轮范围自审通过，可本地提交。仍需另一台电脑更新并重新构建、重启服务，不能声称其 KMeans 任务已经验收。
