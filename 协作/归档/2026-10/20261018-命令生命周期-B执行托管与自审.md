## 根因与生产路径

原 `commandTool` 直接 spawn，超时/停止只 kill 父进程，close 即结算；onSpawn SQLite 记录失败另走 kill/reject，未确认后代。可信检查虽共用该执行器，却无法区分“父进程 0 退出”和“有限时命令完整结束”。记录失败还可能只留下 stopped/普通错误。

现在的真实路径：`assistant-loop run_check → deps.execute(run_command) → control-plane assistantCommands.execute → commandTool → managedCommand → Windows 私有 Job supervisor`；run_command/verify 直接进入同一桥接与执行器。没有迁移员工 CLI、MCP 或自主交付执行器。测试直接组合生产 createAssistantCommands、createAssistantLoop、SQLite 与实际 commandTool；另核对 control-plane 装配使用这份实现，不是手写 unknown 对象代替执行。

## 修改文件与状态

- `src/windows-command.ps1`、`src/windows-command.cs`：固定宿主助手，用系统 PowerShell/Add-Type 调 Windows Job API。监督进程先加入独立随机命名 Job，记录其创建时间，再等待 go，随后启动 worker；后代自动继承 Job。没有设置 breakaway。命令不经隐式 shell，参数按 Windows argv 转义；stdin 关闭，输出独立传输且 UTF-8 解码。
- `src/command-lifecycle.ts`：operationId、首个终态锁存、启动/执行/终止/清理期限、输出截断与脱敏、取消幂等、私有 Job 身份检查与恢复探测。终止检查器返回成功仍须实际查询 Job 活跃成员为零。kill 返回值和父进程 close 均不足以证明完整完成。
- `src/assistant-commands.ts`：生产共用桥接。启动前写 command_intent；监督身份落库后才发 go；启动后身份失败进入同一受控取消。真实输出写现有 assistant_outputs，command_finished 存 outputRef 与事实。最终记录失败抛宿主安全错误，意图保持待核对；项目内存保护明确保留。重启从事件重建门槛；恢复只探测私有 Job 和创建身份，不根据旧 PID 杀进程。
- `src/assistant-tools.ts`、`control-plane.mjs`：保留原参数、超时、输出和秘密边界，接入共用执行器与项目写入/恢复准入。onSpawn 的 PID 现在表示 supervisor，worker PID 单独记入 identity；旧命令 API 参数兼容。
- `src/assistant-loop.ts`：命令不确定性即使用户先停止也进入 attention；busy 释放不解除门槛。主会话及同项目其他会话的受限写入阻断。明确确认、最新版本与现有权限检查后恢复，不重放旧工具。安全事件或状态更新无法落库时返回 runtimeSafety.persisted=false，并保持内存阻断；不宣称错误可靠保存。可信检查最终输出、证据与 verification 更新用 SQLite savepoint，失败回滚，不能留下半个通过结论。
- `src/assistant-verification.ts`：带 operationId 的实际结果还必须 processesEnded、executionComplete、evidencePersisted 均为 true，且无需核对副作用，才有资格 passed。原可信来源、批准、脚本/代码指纹、版本绑定不放宽；旧数据读取兼容。
- `web/assistant-view.ts`：父进程退出 0 但有残留、执行不完整或证据未保存时不显示成功符号；未改布局或其他 UI。
- `test/command-lifecycle.test.mjs`、`test/command-bridge.test.mjs`：真实父进程/后代、就绪信号、SQLite 触发器与生产桥接回归。兜底清理若触发，测试必须失败。
- `test/assistant-verification.test.mjs`：可信检查改走生产桥接，保留原断言并增加失败诊断；`test/assistant-tools.test.mjs`：不误报成功；`package.json`：新测试进入标准清单。CI 已有 Windows、Node 22.19.0、35 分钟外层测试期限与日志上传，未改其范围。

结果区分 exitCode（可为 null）、reason、timedOut/aborted、processesEnded、sideEffectsNeedReview、executionComplete、evidencePersisted，外加会话/项目/operationId/身份/时间/输出引用。普通非零退出但进程完整结束，不要求人工核对，Agent 可修复后重验。父进程 0 退出且后代仍运行则不能成功；强制清除后代也不倒推 executionComplete。

## 有界与 Windows 保证

启动期限 10 秒；实际执行期限沿用工具配置 100–120000 毫秒，监督进程在 worker 启动后计时，宿主另有配置值加 1 秒的后备期限。正常父进程结束后给成员最多 250 毫秒自然退出窗口，输出泵收尾 1 秒；仍有工作则异常终止，不能通过。终止探测器最多 5 秒，Job 活跃数确认最多 1 秒，宿主清理上限 6.5 秒；监督进程还有 2 秒关闭 Job 的后备动作。计时器、abort 监听与输出流释放，迟到事件不改变已结算结果。任何期限或探测失败都明确 unknown，不把 busy=false 或 kill 成功当资源已释放。

Job 的依据见 Microsoft [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)；它是托管机制，不是 OS 沙箱。本轮实测 Windows NT 10.0.26200.0 x64、Node 22.19.0、宿主助手使用系统 Windows PowerShell 5.1.26100.8457（命令终端为 PowerShell 7.6.5）。非 Windows 平台在启动命令前明确拒绝，不沿用无法证明后代终止的旧实现；Linux/macOS 未实现、未执行，属于兼容性限制。Windows 必须可启动系统 PowerShell/Add-Type 并成功加入 Job，否则拒绝/报告未知，不假装已托管。

不支持通过服务、任务计划、WMI、远程代理等外部进程创建者脱离 Job 的后台工作，也不提供后台服务能力。随机 Job 名和监督创建时间用于避免 PID 复用误杀；身份无法核对时不终止不明目标，恢复也不放行冲突写入。

## 数据兼容与剩余风险

不新建任务/Runtime 数据库，不迁移或覆盖旧行，使用现有事件和输出表新增事实。接口字段为增量；exitCode 未知保持 null，旧 verification 与接受状态保持分离。老事件可继续阅读，但基线前的 command_started 缺少 Job 托管身份，无法据此追溯确认后代；原 stopped/restart_interrupted/process_unknown 门槛继续存在。

SQLite 不可用时只能明确保留内存阻断和已有意图，不能保证新未知事件已持久化；需先修复存储再核对恢复。没有模拟整盘物理损坏、系统关机、恶意内核/管理员篡改、跨机器 PID 或 Job 接管。本轮不提供完整输出归档（仍沿用截断预算），未调用收费模型或真实员工 CLI，未迁移其他执行器，也未解决非 Windows 托管。账本和命令门槛均不能代替用户核对部分文件/网络副作用。
