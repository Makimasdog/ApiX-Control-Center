# ApiX 流式对话需求与验收

日期：2026-10-11。状态：需求已记录，待实施与验收。

## 用户需求

用户选择“对话模式”后，可以与 ApiX 进行类似 Codex 的流式对话。本轮将其解释为：在同一目标中连续发送消息，立即看到自己的消息，ApiX 的回复随模型生成逐步出现在同一条消息中，历史可继续阅读和恢复。

“类似 Codex”指聊天交互体验，不要求复制其品牌、界面或内部技术。需求澄清、需求确认、计划审批及任务派发仍使用现有业务规则；发送普通聊天消息不能绕过这些门槛。

## 已有能力与需要完善的部分

现有代码已有 `conversational` 模式、目标聊天历史、POST SSE 和 Pi 增量回调：

- `web/coordinator.ts`：`streamMessage`、聊天输入和消息列表。
- `server.mjs`：`/messages/stream` 发出 start/delta/complete/error。
- `src/apix-agent.ts`：从模型 JSON 的 question 字段提取可展示增量。
- `src/coordinator.ts`：写入用户消息和最终 ApiX 消息；部分状态下会把回复换成固定摘要。
- `control-plane.mjs`：管理者 Pi RPC 和文本增量。

因此本轮扩展现有链路。需处理用户消息到最终刷新才可见、强制滚动、异常后临时回复消失、会话切换结果归属、回复长度限制和预览/最终文本不一致等问题。现有测试事后读取整个 SSE 响应，不能单独证明回复在 complete 前已经实时可见。

## 交互要求

1. 选择对话模式后呈现历史消息与持续可用的输入区域；切入对话模式聚焦输入。约束模式保留现有功能。
2. 发送后立即显示一条用户消息；保存返回后按正式会话去重，不能重复出现。
3. ApiX 回复前显示等待状态；收到 delta 后在同一条 ApiX 消息中累加真实文本，禁止用完整回复加定时动画伪装流式。
4. 多轮对话保留前文。发送新消息不清空已有历史，刷新或重新进入目标可恢复正式记录。
5. 区分待发送、等待回复、生成中、完成、失败；生成中明确阻止重复提交。Enter 发送，Shift+Enter 换行，中文输入法组合态的 Enter 不提交。
6. 用户在底部阅读时跟随新增内容；向上翻历史时不强制拉回底部，提供简单的回到底部操作。
7. complete 到达后采用服务端返回的正式会话和 revision，同步需求摘要等状态；临时回复被正式回复替换。正式文本发生变化时不得将临时内容另存为已完成消息。
8. 模型错误、HTTP 错误、SSE error 或无 complete 的 EOF 均可见；保留可恢复的本轮输入和明确标记的未完成预览，不让失败内容静默消失。服务端可能已保存用户消息，先同步正式会话再允许用户决定是否重发，禁止自动重发导致重复记录。
9. 切换项目/目标时，旧请求结果不能追加到新聊天、清空新草稿或覆盖新会话。可中止旧客户端读取，但不能显示为“模型已停止”；服务端取消不在本轮承诺范围。
10. 正常回复使用适合阅读的段落和列表；如支持 Markdown/代码块，必须安全渲染。模型文本不能直接作为 HTML 执行。
11. 执行阶段允许用户继续询问进度和讨论；采用已知任务状态作为事实来源，不臆造进度，不通过对话擅自修改已确认需求或派发计划。

本轮不加入附件、语音、自动重发、回复编辑/分叉等功能；先完成真实的多轮流式文本聊天。

## 固定接口与事件语义

```http
POST /api/coordination/sessions/:id/messages/stream
Content-Type: application/json

{"revision": 3, "content": "请帮我进一步明确需求"}
```

返回 `text/event-stream`。复用现有事件形状：

| 事件 | data | 语义 |
| --- | --- | --- |
| start | `{sessionId: string}` | 流已开始；不表示用户消息已入库或请求已完成业务校验 |
| delta | `{text: string}` | 可直接追加的 ApiX 可见文本，不包含模型 JSON 外壳或隐藏推理 |
| complete | 正式会话详情，包含 id、revision、turns 等现有字段 | 最终回复和会话状态已保存，以此替换临时预览 |
| error | `{error: string}` | 本轮失败；重新读取会话以判断哪些记录已保存 |

成功流为 start → 零到多个 delta → complete；失败流为 start → 可选 delta → error。非流式模型允许零增量后 complete，但不能宣称其具有逐步生成能力。模型规则降级可通过 complete 正常结束，同时在会话 agent.mode/error 中如实反映。

每个请求最多一个终态。前端处理 HTTP 非 2xx、网络断开、UTF-8 分片、SSE 帧跨 chunk；兼容 LF/CRLF、空行和注释，按边界解析，不能假定每次 reader.read 都是一整个事件。终态之外收到意外事件时不得覆盖其他会话。现有 mailbox GET SSE 与对话 POST SSE 各自保留。

后端保持同一目标的忙碌检查、revision 校验和异常释放。若调整内部回复生成格式或长度，仍要让旧非流式消息接口与最终会话详情保持兼容，正式记录不保存未验证的半截 JSON。

## 分工

- **Codex / C5**：流式通道、模型增量解析、回复/持久化一致性、多轮上下文及状态边界、后端测试 fixture。
- **Claude / L5**：聊天布局与状态、输入与滚动、SSE 客户端解析、会话切换归属、错误恢复和前端测试。
- **Codex / C4**：最终联调、浏览器验证与整体回归，Claude 配合修复前端问题。
