# 2026-10-25 P11 SSE 事件驱动 —— 实施与自审

- **性质**：自审（Codex 口径，非独立审查、非人工批准）
- **依据**：[2026-10-24-问题解决方案.md](2026-10-24-问题解决方案.md) P11（SSE 轮询改事件驱动）
- **环境**：便携 Node v24.22.1；分支 `Kimi/sqlite-ui-polish`

## 1. 变更内容

- **新增 `src/infrastructure/change-bus.mjs`**：进程内事件总线（subscribe/emit，监听器异常互相隔离，不回传写入方）。
- **`src/messaging/mailbox.mjs`**：工厂新增可选依赖 `notify`（缺省空操作，保持可独立实例化）；`appendMessageEvent` 落库后调用 `notify({projectId})`。`agent_message_events` 的全部写入都集中在这一个函数（含 expired/lock/agent.status 等由它派生的事件），因此单一挂钩即可覆盖所有 SSE 可见变化。
- **`control-plane.mjs`**：创建 mailbox 服务时注入 `notify: change => changeBus.emit(change)`。
- **`src/infrastructure/api-routes.mjs`** SSE 处理器：固定 500ms 轮询改为「订阅总线 → 50ms 去抖 → 增量拉取（复用 messageEventsSince 游标）」，保留 **30s 兜底轮询**（防漏发）与 **15s 心跳**（不变）；连接关闭时统一 stop（清定时器 + 退订）；拉取异常时输出 error 帧并停止该流。
- **`test/messaging.test.mjs`**：SSE 测试补两组断言——①事件驱动延迟：已建立的流在写入后 1.5s 内收到游标推进（不依赖轮询周期）；②断线重连去重：`after=最新id` 重连后，重放流中不得出现任何 `id<=游标` 的旧帧，且新事件立即送达。

## 2. 审查结论

- **可靠性等价性**：控制面单进程，所有事件写入与本进程总线同生命周期；30s 兜底轮询保证总线丢通知（理论上不会发生）时仍最终一致。
- **写入路径影响**：notify 是同步 Set 遍历（每连接一个监听器，数量=打开的 SSE 连接数）；监听器仅设置 50ms 定时器，无阻塞操作。
- **时序安全**：去抖定时器 50ms 后才拉取，同步 SQLite 事务届时必然已提交（主线程同步模型）；SSE 处理器内 `stop` 引用的常量均在首次 poll 执行前完成初始化（TDZ 无风险，逐一核对过调用时点）。
- **行为差异**：事件帧内容与到达顺序不变，仅到达时机从「≤500ms 轮询」变为「≈50ms 去抖」；心跳与错误帧语义不变。
- **测试断言修正过程**（如实记录）：首版断言按消息 payload marker 匹配失败——`message.created` 的事件载荷只含元数据（reason/from/to/type），不含消息原始 payload；探针脚本证实推送本身 ~300ms 内到达（含 POST 往返），遂改为按 id 游标推进断言，更贴近真实语义。

## 3.1 coordinator:1337 竞态排查与修复（重要，如实记录）

P11 全量验证时 `authenticated mailbox activity keeps a silent but responsive Agent healthy` 超时，且单独重跑文件仍失败。因 P11 触及 mailbox 事件路径，按回归处理做了严格二分：

1. **对照实验**：`git stash` 暂存全部 P11 改动后，pre-P11 代码同样失败 → 排除 P11 回归。
2. **单用例模式**（`--test-name-pattern`）通过（3.5s）→ 失败依赖同文件长上下文，非确定性逻辑错误。
3. **量化**：裸 node spawn 仅 ~40ms，但 worker 夹具冷启动（进程 + 首轮认证 fetch）在长上下文/慢环境下可超过用例的 800ms 静默窗口，agent-health 先判 unresponsive → 任务变 unknown → 等待 completed 超时。该用例 2026-10-24 报告 R1 即记录过同样失败（当日 P11 之前），当天上午第一轮全量也复现过。
4. **修复**：该用例静默窗口 800→1500ms（worker 心跳总时长 2200ms，语义不变；unresponsive 路径由上一用例继续以 800ms 验证）。修复后连续 2 次全文件 75/75。
5. 排查期间另见一次一次性 server 启动卡顿（startup_deadline，连接被拒 9s），重试即过、未再现，判定为当日连续 ~8 轮全量测试后的环境性抖动，未改代码。
