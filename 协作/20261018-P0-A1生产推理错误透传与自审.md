# P0-A.1：生产推理包装中的模型资源未知错误

## 基线与根因

开始时分支 `codex/readiness-p0-p2`，HEAD 为 `c2e1ad1633085a4cb76872351d121ab3722005c6`，与审查基线一致，没有后续提交差异。已读取 AGENTS、模型后端、主循环恢复/互斥、control-plane 两层包装、相关测试、package、CI 及 P0-A 自审。Codex 实施并自审，不启动其他 Agent，不称独立审查或人工批准。

核实真实链条：`inferModel → inferManager → createAssistantLoop 装配的 infer 回调 → kick`。底层产生 `MODEL_CLEANUP_UNKNOWN`，inferManager 保留它，但外层回调脱敏后 `new Error(message)` 丢失 code。此前直接替换 `h.deps.infer` 的测试绕过了这个生产包装，不能证明完整链条。running 会话缺少 process_unknown，已停止会话可只保留 stopped；busy 清空不能证明模型资源安全释放。

先把生产包装和 inferManager 的错误选择分支原样提取，保留缺陷，再运行失败用例。修复前实际结果 **7 项：3 通过、4 失败**，日志 `.tmp-p0-p2/p0a1-before.log`：

- 真实本地 HTTP 清理未知经过包装后 code 为 undefined。
- running、stop 后及权限撤销三个组合场景分别未建立资源未知门槛；其中 stop 后仍为 stopped。
- 生产装配绑定、普通错误/费用及正常停止的对照用例通过。

只允许宿主 `ModelCleanupUnknownError` 实例保留 `MODEL_CLEANUP_UNKNOWN`；普通 Error 或供应商 JSON 即使含同名 code，也不能升级为资源未知。类型判断不依赖中文文案。新错误仅带脱敏且最多 1000 字符的 message 和固定宿主 code；不转移原 cause、body、额外字段或 stack。inferManager 的权限提示不能覆盖该宿主类型。

不新增数据库表或任务状态，不改 assistant-loop：现有 kick 一旦收到该 code，就写入 `process_unknown {resource:'model_transport'}`，转 attention 并释放 busy。现有持久化事件、message、项目写入互斥和 resume 的明确确认/版本检查恢复作用。恢复后重新获取决策和必要批准，不自动重放旧工具。

## 生产实现被测试的依据

测试直接导入生产 `createAssistantInference` 和 `managerInferenceError`，control-plane 的装配实际使用相同导出；另有装配绑定断言防止测试代码与生产接线脱离。没有另写等价错误包装，也没有仅向 `h.deps.infer` 注入带 code 的错误。

关键路径由真实 `inferModel` 请求本地 HTTP：测试仅在底层 socket 边界抑制 close 确认，实际 socket 仍销毁。模型已给出写入决策，但清理未知阻止决策执行。running、stop 后、权限撤销组合均穿过生产适配器和主循环；权限撤销组合调用生产错误选择函数，未另写其分支。没有新增生产 HTTP 客户端能触发的故障开关。

SQLite 使用临时文件，关闭并重新打开连接/主循环后，unknown 事件仍存在、busy=false、attention 保留，普通消息及同项目另一会话写入仍被阻止。明确核对需当前版本及 confirmed=true；核对后不执行旧决策。新写入仍需新的当前权限批准，旧权限版本批准被拒绝。

资源夹具有 4 秒 watchdog、测试有 5–7 秒期限、定向文件有 15 秒外层期限。进入响应阶段用真实 onDelta 信号；watchdog 拒绝阶段信号并标记失败，不允许测试依赖夹具取消而通过。finally 恢复底层方法和环境变量、关闭连接/服务器/数据库并校验临时目录后删除。普通 JSON 协议错误、第三方同名 code、清理确认成功的停止均不产生 process_unknown。
