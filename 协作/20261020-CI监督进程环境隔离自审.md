## 原因、修复和边界

原 managedCommand 把项目的裁剪环境直接用于启动 PowerShell 监督程序。监督程序会先初始化 PowerShell/.NET 并 Add-Type 编译固定 C# helper，尚未创建任务 Job 或启动 npm；它的初始化却受项目私有 HOME/TEMP、缺少模块/缓存等宿主环境信息影响。CI 现象与该耦合吻合。没有抓取 CI 每个 PowerShell 内部模块的耗时，故不冒称确定具体哪次模块扫描或 .NET 调用耗满十秒。

修复只分离两份环境：

1. `command-lifecycle.ts` 用宿主环境启动固定的可信 PowerShell helper，把原本选择的项目环境通过私有 stdin 配置传递。
2. `windows-command.ps1` 在初始化完成后解析环境配置，传给 C# Run。
3. `windows-command.cs` 在受管命令启动前清空 ProcessStartInfo.EnvironmentVariables，再只填入选择的环境；不会把宿主凭据、NODE_OPTIONS 或用户 npm 配置补进项目进程。

项目环境/安装策略和批准语义不变；没有改启动十秒门槛、单命令期限、Job 身份记录与 go 握手、取消/未知判定、SQLite 终态或验收规则。Inspect 仍不运行项目命令。环境配置不进入 SQLite/工具输出；现有输出脱敏同时覆盖宿主和项目环境中的敏感值。PowerShell helper 属于持有宿主凭据的可信程序，不宣称其本身是沙箱；项目命令仍遵守所选环境边界。

生产调用链已核对：assistant-tools.commandTool → managedCommand → 固定 PS1 → C# Run，只有该 PS1 调用 Run；所有执行调用方继续用原签名，新增内部环境参数不向模型开放。同步更新 Node/npm 使用文档，避免把监督程序初始化和项目环境混为一谈。
