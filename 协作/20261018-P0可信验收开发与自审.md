## 实现与状态转换

1. 模型可以提出 `configure_verification {checks:[{id,args:[项目内Node脚本,...参数],timeoutMs}],writablePaths:[相对文件或目录]}`。即使 full_access，也必须走现有用户批准弹窗。批准绑定会话/工具/权限版本、代码指纹以及冻结文件草案；批准期间文件变动则旧请求失效。
2. 用户批准后，宿主在既有 assistant_events 保存项目契约。所有 checks 都是必要检查，没有模型可选的“跳过必需检查”。契约不授予员工权限、提升项目模式或费用额度。现有多 Agent 检查格式得以复用，但其旧授权不会静默升级成新主 Agent 契约。
3. `run_check {checkId}` 只执行契约固定的 Node 命令；额外模型参数不能覆盖命令。使用现有 commandTool 和环境隔离，不隐式 shell。退出码必须明确为 0，timedOut/aborted/unknown 必须明确为 false；检查前后代码及冻结契约须相同，且会话仍在运行、权限版本一致。
4. 每次检查记录 sessionId/runId、checkId、契约版本、来源、命令、时间、退出码、中断标志、项目指纹、passed、verificationStatus、outputRef。开始记录先持久化；实际输出以带摘要的 assistant_outputs 保存并按原会话权限读取。不是 LLM 生成的测试证言。
5. `finish completed` 对修改任务从事件重新计算必要检查集合及版本，不信任旧 verification 字符串。`write_file`、命令和 MCP 的后续执行会使此前证据失效，即使写回相同内容。契约重新批准也要求重新执行检查。技术验证 verified 可以完成当前工作；它不设置任务 accepted。
6. 无契约或冻结范围失效：attention / needs_review，宿主显示未可信验证，不展示模型的完成断言。检查失败：反馈证据，在原 24 步、30 分钟、权限与预算内修复重验。超时、停止、进程未知：保留实际失败/未知证据，要求检查后恢复；重启不自动重放。只读问答仍可直接完成。此前无待验证修改、普通诊断进程结果明确且前后代码指纹相同，也可保持 not_required；这不是可信通过，不能替已有修改免验。

## 兼容性与风险

- 不新增任务状态数据库或运行时，不迁移/删除旧数据。复用 assistant_events / assistant_outputs 和原 verification 字段；旧字符串不能独立授信。既有 API 字段保留，增加 verificationStatus、contract、checks、acceptanceStatus；无可信证据时对外 verification 为 null。工具 Schema 版本改变后，已有待批准请求可能须拒绝并重新申请，不能沿用旧版本批准。
- 不修改 autonomy / 调度器及员工适配器，不重新引入 Pi 依赖；MCP/审批/上下文继续走原路径。单 Agent 正式 acceptance 没有新增自动路径，避免把技术验证等同用户接收交付。
- P0 限项目内 Node 检查及现有完整扫描预算：3000 项、8 MiB、单次 100–120000 毫秒；冻结扫描包含本地依赖和临时目录，Git 元数据除外。大型依赖树可能拒绝授信，需要人工审查或既有委派流程；未悄悄忽略依赖变化。
- 没有新增 OS 沙箱、隔离测试快照或进程树治理。外部程序、网络状态、Git 元数据和项目外依赖不在快照保证内；前后指纹不能证明不存在瞬时改动再还原。用户应批准具有实际业务断言、依赖清晰的检查，机制不证明检查覆盖充分，也不能保证任意不可信程序不恶意作弊。
- 输出沿用 commandTool 的有界采集与脱敏，outputRef 保存真实已采集结果及 truncated 标志，不宣称保留无限原始日志。浏览器布局与真实付费模型/员工版本未在本轮额外验收。
- 标准全量存在上述模型响应体超时/取消用例的间歇阻塞，独立复测通过但根因未确定；不能声称全量回归稳定通过。远程 CI、真实 qwen3.8-27b、真实 Codex/Claude CLI、多系统和长期运行均未在本轮执行。
