# ApiX 交互与多 Agent 协作优化

更新：2026-10-11。用户要求同时优化任务分配、Agent 协作和用户交互。项目中的多 Agent 功能由 Codex 单独开发；不启动真实 Claude 或子 Agent。

## 本轮范围

| 方向 | 改动 | 验收 |
| --- | --- | --- |
| ApiX 拆解与分配 | 规划提示明确任务范围、输入、交付物、证据；无依赖且文件不重叠的步骤可并行；优先安排另一位合适员工审查 | 实际规划模块可解析双并行入口及汇合依赖；提示策略不等于模型保证 |
| Agent 上下文交接 | 已确认需求与消息协议完整保留；前置交付物分别带来源 ID，并与其他参考资料共享剩余预算 | 大交付物保留多个来源，截断显式标记；必需上下文超限在进程启动前拒绝 |
| Agent 消息可靠性 | 每次领取只标记实际返回批次；未确认消息可重复投递，确认后释放领取额度 | 隔离 HTTP 验证限额、重投和未返回消息保持 queued |
| 用户与 ApiX 对话 | 推理接收真实状态、依赖、监督记录和待验收关系；规则进度回复区分执行、待验收、已验收和异常 | 隔离 HTTP 检查推理输入与需求版本不变 |
| 前置验收门槛 | ApiX 目标计划与协作计划统一等待 accepted；验收拒绝会阻塞下游，不创建下游进程 | 新增隔离 HTTP 验证接受后推进与拒绝后阻塞 |
| 用户执行进度 | 异常任务优先显示需要处理；任务卡展示未验收的前置编号 | 实际模块回归；隔离页面已验证等待、通过后推进和拒绝后阻塞 |

流程：用户讨论 → 确认需求 → ApiX 生成可编辑计划 → 批准 → 并行入口执行 → 验收前置交付物 → 推进后续步骤 → 最终验收。各员工的权限与需求版本仍由服务端校验。

## 重要边界

- 各任务仍使用独立工作区。传递报告不会自动同步代码；本轮明确告知这一边界，未实现自动代码交接。
- 消息保持至少一次投递语义，员工须及时 ack/complete 并按消息 ID 避免重复处理；不宣称恰好一次交付。
- 未确认消息可能占用领取额度，直到确认、失败或过期；这是显式背压，不会把未返回消息误记为 delivered。
- 模型决定是否并行、如何安排审查；服务端继续验证可用员工与合法依赖。本轮没有宣称强制文件所有权锁或独立审查。
- 本轮不新增自动重试真实任务、自动扩大授权、自动推送或合并行为。

## 后续开发顺序

1. **运行级消息路由**：同一个员工同时执行多个任务时，按 run/task 隔离指导消息；定义跨任务交接信封与目标任务校验，保留项目边界。
2. **代码交接**：依据前置验收产物生成可审查 patch，明确基线、集成工作区、冲突与失败处理；依赖步骤须在集成完成后取得正确代码。
3. **执行资源与恢复**：按员工和项目限制并发；区分可重投消息与不可直接重跑的执行任务，定义额度不足、超时、取消和重启恢复。
4. **真实多 Agent 验收**：真实运行时可用后验证分配、报告、接收指导及集成；与模拟 CLI 结果分开记录。
