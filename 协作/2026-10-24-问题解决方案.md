### P5 修复 413 ECONNRESET（新发现 bug）

**根因**：`server.mjs` 读 body 的循环在超限时立刻 `throw`，处理器在请求体未读完时响应并返回；Node 随后销毁未排空的 socket，同连接池的下一个请求得到 `ECONNRESET`。

**方案**（三处 body 读取循环统一改为一个工具函数）：
```js
// server.mjs 顶部
async function readBody(request, maxBytes, over) {
  let raw = '', tooBig = false;
  request.setEncoding('utf8');
  for await (const chunk of request) {
    raw += chunk;
    if (Buffer.byteLength(raw) > maxBytes) { tooBig = true; raw = ''; } // 超限后丢弃，继续排空
  }
  if (tooBig) throw over(); // 请求体已完整消费，socket 可安全复用
  return raw;
}
```
配合 P7 的路由表把每条路由的 `maxBytes`（普通 30K→见 P13、知识上传 1.5M）作为参数。若不想等重构，最小修复是仅在超限分支加 `response.setHeader('Connection','close')` 并保留 throw。

**回归测试**（加进 `test/tool-knowledge.test.mjs`）：
```js
// 413 之后同一 keep-alive 连接的下一个请求必须成功
const over = await fetch(upload, {...1.6MB...});       // 413
const next = await fetch(toolAccess);                   // 必须 200，不得 ECONNRESET
```
- 验收：上述测试通过；原冒烟复现脚本 413 后连续 3 个请求全部成功。
- 工作量：2 小时（含测试）。

### P9 前端渲染安全兜底（替代手动 esc()）

现状：UI 全靠每处手动调 `esc()`，漏一处就是 XSS；且无框架默认转义。
1. **低成本方案（推荐先行）**：引入 20 行的自动转义 tagged template：
   ```ts
   // web/html.ts
   export const html = (strings: TemplateStringsArray, ...values: unknown[]) =>
     strings.reduce((out, s, i) => out + s + (i < values.length ? esc(values[i]) : ''), '');
   // 用法：element.innerHTML = html`<strong>${name}</strong>…`  // 插值全部自动转义
   ```
   ESLint `no-restricted-syntax` 禁止 `innerHTML =` 后跟含 `${}` 的普通模板串（P4 已加规则位），新代码强制用 `html`；旧代码按文件渐进迁移（knowledge.ts 这类新文件先改）。
2. **中期选项**：新视图（如后续知识库扩展）可用 preact+htm（~4KB，无需打包器，ESM 直引本地 vendor），仅限新文件试点，不做整库迁移。
- 验收：lint 生效；`verify-tool-knowledge.mjs` 的转义断言继续通过；抽查 3 个新视图无裸 `${}` innerHTML。
- 工作量：1 天（helper+lint+迁移 knowledge.ts）。

## §3 架构

### P10 SQLite 主线程阻塞

现状：`DatabaseSync` 全同步 + WAL 已开；知识库索引（≤700 块插入）虽在单事务内但仍在主线程，索引 1MiB 文档期间事件循环停摆。
1. 先测量再优化：给知识库 `queue()` 加耗时日志（分块/入库两段），`node --cpu-prof npm start` 复现索引负载下的 UI 延迟，拿到基线。
2. 若实测阻塞 >100ms：把 `parse + 入库` 移入 `worker_threads` Worker（独立连接开同一 sqlite 文件，WAL 允许一写多读；主线程只收 `{docId,state}` 结果回写）。注意与主线程写错峰：Worker 内写 `kb_*` 表，主线程仅读。
3. SSE 轮询查询（见 P11）改事件驱动后，数据库稳态读压力趋零，无需更多优化。
- 验收：索引 1MiB 文档时 `/api/snapshot` p95 <100ms；文档状态仍正确走 processing→ready/failed。
- 工作量：测量 0.5 天；Worker 化 1-2 天（视测量结果决定是否做）。

### P11 SSE 轮询改事件驱动

现状：每连接 `setInterval(writeEvents, 500)` 查库。单用户本地可接受，但空闲 CPU 与连接数成正比。
1. 进程内事件总线：控制面所有写入 `assistant_events`/`message_events` 的提交点调用 `bus.emit('db-change', {projectId, agentId})`（写入路径集中在本进程，可靠性等同轮询）。
2. SSE 订阅 `bus`，50ms 去抖后执行现有 `messageEventsSince` 增量拉取；**保留 30s 兜底轮询**防漏发。
3. 心跳保持不变（15s）。
- 验收：事件端到端延迟 <100ms；空闲时（无写入）CPU 占用归零；断线重连去重行为不回归（`test/messaging.test.mjs` 补断言）。
- 工作量：1 天。

### P12 测试分层提速（全量 ~8 分钟 → 目标 <5 分钟）

1. 按启动成本分目录/标签：
   - `test/unit/`（纯模块级，经 dist 直测函数，不起服务器、不建 git 仓库）——去掉 `--test-concurrency=1`，允许并行；
   - `test/http/`（真实起 server.mjs 的集成测试）——维持串行。
   现有 56 个文件逐一归类（多数 coding-*/command-* 本就是进程内 fixture，归 unit；agent-os/coordinator/conversation-ui 等归 http）。
2. `npm test` 改为两段：`node --test test/unit/...`（并行，~1 分钟）→ `node --test --test-concurrency=1 test/http/...`。
3. 目录迁移用 `git mv` 保持 blame；`package.json` 列表改目录通配（node --test 支持目录参数）。
- 验收：CI 总时长明显下降（目标 <6 分钟）；无测试因并行互扰偶发失败（连跑 3 次验证）。
- 工作量：1 天（主要是归类与验证并行安全）。

### P13 请求体限额语义统一

现状：普通路由硬编码 30000 字符（长对话粘贴易被拒），知识上传 1500000，语义分散。
1. 借 P7 路由表把 `maxBytes` 变成路由属性，集中一张表可审计：
   - 对话消息类（messages/reply/compact）：256KB（覆盖粘贴长日志）
   - 配置类（settings/providers/permissions）：64KB
   - 知识上传：1.5MB（现状保留）
   - 其余默认：30KB
2. 同步更新测试断言（现有 30000 相关负例）与 README「配置指南」的限额说明。
- 验收：超限各回 413/400 且**无 ECONNRESET**（P5 测试覆盖）；255KB 消息可发送成功。
- 工作量：0.5 天（依赖 P5/P7 先行）。

## §4 产品与文档

### P14 功能完成度：冻结面、定义完成标准

1. **冻结新功能面**一个周期（如两周），只修本报告问题 + 打磨三条核心回路：
   - 回路 A：配置供应商 → 对话 → 工具执行 → 验收

2. 给每个功能建"完成标准"三件套：契约文档（哪个文件）、验收脚本（`scripts/verification/verify-*.mjs` 之一或新增）、已知限制清单。已有 verify 脚本的功能补齐另两样即可。
3. 加一个聚合脚本 `test:ui:all` 串跑全部 verify-*.mjs，作为发布前检查。
- 验收：三条回路各有可重复执行的验收脚本并在 README 链接；`test:ui:all` 绿。
- 工作量：脚本聚合 0.5 天 + 回路打磨按发现计。

### P15 文档索引与归档

1. 建 `docs/INDEX.md`：一张表 = 功能 | 状态(active/beta/frozen) | 契约文档路径 | 最新验收记录 | 已知限制。首版从 README「核心功能」表 + `协作/` 目录各验收文档标题生成。
2. `协作/` 已归档习惯（`docs/归档/`）推广：被新文档取代的验收记录移动归档并在 INDEX 标注 superseded。

- 验收：INDEX 覆盖 README 功能表全部条目；新贡献者 10 分钟内能定位任一功能的当前契约。
- 工作量：0.5 天（生成首版）+ 每次提交 5 分钟。
